## 1. 一句话美学主张

> **这是一个「暗房里的档案柜」——照片是藏品本身，界面是贴在照片旁边的索引卡，而不是一个装照片的网页。**

展开成三条可执行的原则：

1. **照片是唯一发光体。** 界面所有中性色都压在 HSL L≤16.7% 的暗部区间（相对亮度 Y≤0.021），比最暗的 5% 图片（Y=0.217）还暗 10.4 倍。界面负责「不打扰」，不负责「好看」。
2. **信息是档案，不是装饰。** 目录名里真实存在的语法（coser / 主题 / 数量 / 体积 / 标签）必须被**拆解并重新赋予层级**，而不是原样打印成一坨字符串。而且——**展示的必须是实测值，不是目录名的声明值**（实测证明声明值只有 20.5% 成立）。索引卡的排版精度，是这个产品全部的视觉价值所在。
3. **冷色工具，暖色内容。** 工具部分（导航、筛选、控件）一律冷调去饱和，把全部色彩预算留给照片本身。

**审美坐标**：Netflix/Disney+ 的「海报墙」是影视流媒体的语法；Pinterest 的「瀑布流」是灵感聚合的语法。本项目两者都不用——它是**本地归档与检索**工具，参照物是摄影暗房的接触印样（contact sheet）与图书馆的卡片目录：安静、致密、信息优先、无推荐流。

### 2.3 色彩规则（硬约束）

1. **界面里不允许出现纯黑 `#000`**，也不允许出现纯白 `#FFF` 作为大面积背景。照片才是画面里最亮和最暗的东西。
2. **强调色只有一个**（冷青蓝）。琥珀色是「档案章」，只在数量/体积/日期这类物理属性上出现，**绝不用作按钮底色**。
3. 界面中性色的色相锚定在 **H218–231**（冷灰蓝）。素材自身是暖中灰（`#8A7D7C`，H3.9°），冷界面与暖图片形成稳定的温度对立。
4. 任何 UI 元素的填充色，HSL 饱和度 **≤ 50%**，明度 **≤ 64%**。超过就是跟照片抢。
5. 深浅主题共用同一套语义 token 名，只换值。禁止在组件里写死 hex。

### 2.4 图片区与 UI 区的「明度/饱和度分离」执行

| 区 | 明度区间 | 饱和度 |
|---|---|---|
| 图片区（照片本身） | 相对亮度 Y 0.217（p05）– 0.763（p95） | 自由，素材本身饱和度从 0.05 到 0.9 都有 |
| UI 区（表面层） | 相对亮度 Y 0.0027–0.0208 / HSL L 3.7%–16.7% | S ≤ 15.8%（全部是冷灰） |

暗色主题表面层相对亮度阶梯（用于校验「分层靠明度」是否成立）：

| 层 | Hex | 相对亮度 Y |
|---|---|---|
| `--bg-void` | `#08090B` | 0.0027 |
| `--bg-base` | `#0E0F12` | 0.0048 |
| `--surface-1` | `#16171B` | 0.0086 |
| `--surface-2` | `#1E1F25` | 0.0139 |
| `--surface-3` | `#26282F` | 0.0208 |

这个分离带来的具体效果：暗色主题下**最亮的 UI 表面**（`--surface-3`）相对亮度仅 Y=0.0208，而**最暗的 5% 图片**平均亮度也有 0.217 —— 相差 **10.4 倍**。也就是说，**没有一张图片会比界面暗**，图片在暗底上必然呈「发光」状态。加上每张图 1px 的 `rgba(255,255,255,0.08)` 内描边，图片边缘形成一圈「相纸边缘」，这是照片墙不发糊的关键。

> 对比浅色主题：`--lt-bg` Y=0.8957，比中位照片（0.527）亮 **1.7 倍**。这就是浅色模式必须额外加强边框与阴影的原因（见 §7.1、§8）。

## 3. 从素材库提取的主色调如何进入设计

**素材色彩气候（已完成回填 · 两套独立方法交叉验证）**

> 本节数据由**两套完全独立的方法**测得并互相印证：
> - **像素级**（设计侧）：随机 420 个目录 × 3 张 = 1,254 张，64×64 采样，共 3,459,136 像素，按色相家族统计
> - **图像级**（主理人并行分析，`_analysis/palette.json`）：每图主色聚类 + 饱和度/明度/对比度中位数
>
> 两套方法结论一致，§3 的所有设计决策均建立在这条已验证的链路上。

**设计侧自测样本**（随机 420 个目录 × 每目录 3 张 = 1,254 张，64×64 缩略采样，共 3,459,136 像素）

**色相家族分布（全体像素）**

| 家族 | 占比 | 家族 | 占比 |
|---|---|---|---|
| 橙 (15–45°) | **31.3%** | 紫 (255–290°) | 4.4% |
| 蓝 (195–255°) | 24.1% | 绿 (75–165°) | 4.3% |
| 红 (345–15°) | 21.9% | 黄 (45–70°) | 4.0% |
| 粉 (290–345°) | 6.7% | 青 (165–195°) | 3.3% |

**高饱和像素（S>0.35）分布**：橙 41.1% · 红 25.3% · 蓝 22.4% · 粉 3.3% · 青 2.3% · 紫 2.2% · 黄 1.8% · 绿 1.6%

**色彩统计量**：全库平均色 `#8A7D7C`（H3.9° S5.7% L51.6%）；单图平均饱和度分档 —— 低(<0.18) **67.7%** / 中(0.18–0.45) 29.6% / 高(>0.45) 仅 2.6%

**这组数据如何转化为设计决策：**

| 观察 | 设计决策 |
|---|---|
| 素材色相 60% 集中在橙+红+粉，且**高饱和区更极端**（橙红合计 66.4%） | UI 主强调色**必须冷**。任何橙/红/粉的强调色都会与照片争夺注意力，且在不同照片上表现不一致 |
| 青（3.3%）与绿（4.3%）是素材里最稀缺的色相 | 选中态、焦点环、链接选用 **H188–190 冷青蓝**——它在素材里几乎不存在，所以永远不会被误认成「照片里的颜色」，同时又与冷灰界面同族 |
| 全库平均饱和度仅 5.7%，67.7% 的图片平均饱和度 < 0.15 | 界面**不要**上高饱和色。冷青蓝 S49.8% 是上限；再高就会显得像另一个产品贴在了照片上 |
| 全库平均色是暖中灰 `#8A7D7C`，而图片中位亮度 0.527 属中高调 | 界面明度必须压到最亮表面 Y=0.0208 以下（HSL L≤16.7%），照片才能始终处于「比界面亮」的状态 |
| 素材本身偏暖（平均 H3.9°），界面平均 H≈225° | 形成 **暖内容 / 冷工具** 的稳定温度对立。这是本方案最核心的一条色彩原则 |

**交叉校验：与 `_analysis/palette.json` 的独立分析一致**

主理人的并行分析（`_analysis/palette.json`）用不同方法得到同一结论，两组数据互相印证：

| 指标 | 设计侧自测（像素级） | palette.json（图像级） | 一致性 |
|---|---|---|---|
| 暖色占比 | 63.9%（橙31.3+红21.9+粉6.7+黄4.0） | `warm: 0.6625` | ✅ |
| 冷色占比 | 31.7%（蓝24.1+青3.3+绿4.3） | `cool: 0.03125`（冷色**极稀缺**） | ✅ 方向一致 |
| 中位饱和度 | 单图中位 ≈ 0.217 | `median_sat: 0.247` | ✅ |
| 中位明度 | 单图亮度中位 0.527 | `median_val: 0.610` | ✅ |

**关键差异（必须说明）**：`palette.json` 的 `accent` 列表是**从素材里提取的代表性色彩簇**（`#FE00E0` 洋红 S100%、`#F22E01` 橙 S99.6%、`#00C8C5` 青 S100% 等），它们的饱和度是 68–100%，**是照片里的颜色，不能直接当 UI 色**。按 §2.3 的硬约束（填充色 S≤50%、L≤64%、且避开暖色区）逐条筛查这 10 个候选，**只有 `#605F91` 通过**——而它是紫调（§9 禁用项 ②）。

本方案的 `#4FB3C4` 恰好落在这批素材色的**色相邻域**：与 `#00C8C5`（H179.1）同族但把饱和度从 100% 压到 49.8%、明度压到 53.9%；与 `#34718D`（H198.9）色相邻但更亮更饱和。**换句话说：UI 强调色是素材冷色簇的「低饱和版本」**——既保留了与图片同源的色彩血统，又不会在暗底上喧宾夺主。

**反向结论（明确排除的方案）**：
- ❌ 暖色强调（琥珀/橙/砖红）——与素材 31.3% 的橙色像素直接冲突
- ❌ 冷紫/靛蓝强调——虽然不撞暖色，但 H255–290 的紫在素材里占 4.4%，且紫调在暗底上会营造「赛博」气质，与「暗房档案」主张相悖
- ❌ 用素材平均色 `#8A7D7C` 作为界面色——那会让界面和照片同温同调，分离感归零

```
             "Hiragino Sans GB", sans-serif;

/* 元数据 / 路径 / 数量（等宽） */
--font-mono: "JetBrains Mono", "SF Mono", "Cascadia Mono", "Menlo", "Consolas",
             "PingFang SC", "Microsoft YaHei", monospace;
```

- 不引入 Web Font 文件。5,292 个目录 + 3,377 个标签的中文渲染需要系统级 CJK 字体栈，网络字体会因字重不足导致 CJK 回退抖动。
- **所有数量、体积、日期、文件尺寸、路径一律用 `--font-mono` + `font-variant-numeric: tabular-nums`**，让右对齐的数字列能上下对齐——这是档案感的技术来源。

### 4.3 中英混排规则

1. **CJK 正文行高 ≥ 1.68**（13/22 = 1.69）。中文是方块字，没有拉丁文的 ascender/descender 留白，行高不足会显得拥挤。
2. **CJK 正文禁止 letter-spacing > 0.02em**。字距一旦拉开，中文的字面方格节奏被破坏，会出现「散架感」。拉丁文部分单独用 `letter-spacing: 0.01em`。
3. **中英之间需要视觉间隙**：优先使用 `text-autospace: normal`（渐进增强）；不支持时，在构建字符串时于中西文边界插入 1/8 em 的 hair space（`\u200A`）。不要用 `margin` 硬撑，会在换行时留下空隙。
4. **数字与单位不分离**：`1280×853`、`86P`、`1.38G` 中的单位与数字同字体同色，中间不加空格。
5. **`#` 前缀在渲染层剥离。** 5,292 个目录、3,377 个标签若都显示 `#`，全是噪声。`#` 的语义由胶囊样式承担。
6. 标题超过 1 行截断时用 `text-overflow: ellipsis`，**不做两端省略**——中文目录名两端都是关键信息。

### 4.4 目录名的解析与重排（本产品的核心排印逻辑）

真实目录名的语法（两个根目录略有差异，必须统一处理）：

**索引字段与本规范语义的对应关系**

| 本规范语义 | 索引字段 | 类型 | 覆盖套图数 | distinct 值 | 数据特征 |

**实测标签密度**：平均每套图 **1.34** 个标签；分布为 0 个 → 1,367（25.8%）、1 个 → 1,915（36.2%）、2 个 → 1,147、3 个 → 636、4 个 → 184、5+ → 43。
→ **25.8% 的套图没有任何标签**，卡片标签行必须能整体缺席而不留空槽（见 §5.1「卡片高度恒定」）。

**⚠ 规则一：声明值与实测值必须分开处理（最容易做错的一处）**

实测证明目录名里的方括号计数**不可信**：

| 事实 | 数值（n=551 抽样） |
|---|---|
| 声明数与实际数完全一致 | **0.7%** |
| 实际少于声明 | **95.3%** |
| 实际多于声明 | 4.0% |
| 按总量计算的图片到位率 | **20.5%**（单目录填充率中位 0.23，p10 仅 0.06） |

实例：`#Bangni邦尼 圣诞甜心 80P3V2.98GB` 这个目录实际只有 **7** 张图。

因此：
- **卡片、详情、筛选分面一律使用实测张数**（扫描文件系统得到），不用目录名声明值。
- 声明值可以保留，但只能作为**次级信息**呈现，且必须显式标注为「来源声明」，例如详情抽屉数据表里放一行：`图片数 7（本目录声明 80）`。
- **`V`（视频）计数在全库范围内没有任何对应文件**（85,404 个文件里只有 JPEG 与 11 个 `.part` 分片，0 个视频）。因此**界面不设计任何视频相关 UI**：筛选侧栏不出现「视频」维度，徽章不出现 📹，统计不出现视频条目。声明里的 `3V` 在解析阶段直接丢弃。这是一条**功能减法**决策，不是遗漏。
- 体积声明（`2.98GB`）同理不可信，不作为筛选维度；体积维度应基于实测字节数（实测单图 p50 129KB）。

**重排后的视觉结构（这是与「直接显示目录名」的本质区别）：**

以 `#Bangni邦尼 圣诞甜心 80P3V2.98GB` 为例（该目录实测 **7** 张图，声明 80P）：

```
┌─────────────────────────────────────┐
│                                     │
│           封面图 3:4                │   ← 图片，唯一发光体
│                                     │
├─────────────────────────────────────┤
│ Bangni邦尼    圣诞甜心               │   ← ① coser 胶囊（强调色，# 已剥离） ② 标题 14px/600
│ 7 张 · 2026-03-22                   │   ← ③ 实测张数（琥珀 mono） ④ 实测日期
│ 碧蓝航线 · 柴郡 · 兔女郎  +3         │   ← ⑤ 标签片（中性，# 已剥离）+ 溢出计数
└─────────────────────────────────────┘
```

层级规则：
- **coser 胶囊**用强调色（`--accent-wash` 底 + `--accent-hover` 字）——它是套图的主键，也是跨目录重复最多的元素。
- **标签片**用中性（`rgba(255,255,255,0.055)` 底 + 1px `rgba(255,255,255,0.07)` 边）——2,794 个长尾 `others` 值不能有色彩噪音。
- **数量/日期**用琥珀色 mono —— 它们是「这张卡的物理档案号」，且**必须来自实测**（见上方规则一）。
- **渲染时全部剥离 `#`**（见 §4.3 第 5 条），`#` 的语义由胶囊/标签片的样式承担。
- 标题最多 1 行；标签最多 3 个 + `+N`。

**⚠ 规则二：标签的显示优先级必须按「语义价值」而非数组顺序**

索引返回的是 8 个并列数组，**不能按字段顺序直接拼接**。因为 `others`（泛化词）占 50.1% 覆盖却信息量最低，而 `works`（24 个作品 IP）基数极低却是最强检索维度。卡片的标签行排序固定为：

| 优先级 | 来源 | 理由 | 上限 |
|---|---|---|---|
| 1 | `works` | 作品 IP 是最强检索入口（碧蓝航线/原神/NIKKE…） | 1 个 |
| 2 | `roles` | 角色名（柴郡/2B/甘雨…） | 1 个 |
| 3 | `themes` | 主题（兔女郎/女仆/旗袍…） | 1 个 |
| 4 | `others` | 泛化词，仅在前面为空时补位 | 剩余名额 |
| 5 | `times` / `co` / `alias` / `emoji` | **卡片上不显示**，只在筛选侧栏与详情出现 | 0 |

`works` 只显示 1 个是有意为之：作品 IP 在同一套图里几乎不会重复（`works>1` 仅 42 套，0.8%），给一个位置就够，剩下留给角色与主题。

**⚠ 规则三：标签归一化必须在展示层完成（否则筛选器会出现重复项）**

索引里存在同一标签的大小写/符号变体，直接渲染会导致筛选项重复。已实测到的变体：

| 分类 | 变体 | 合并后 | 出现次数 |
|---|---|---|---|
| `works` | `NIKKE` / `Nikke` / `nikke` | `nikke` | **91** |
| `works` | `FGO` / `fgo` | `fgo` | 46 |
| `roles` | `艾莲乔` / `艾莲·乔` | `艾莲乔` | — |
| `roles` | `柴郡绚烂夜梦` / `柴郡·绚烂夜梦` | `柴郡绚烂夜梦` | — |
| `themes` | `JK` / `jk` | `jk` | — |
| `others` | `MIKU` / `Miku` / `Miku` | `miku` | — |
| `others` | `尼尔·机械纪元` / `尼尔机械纪元` | `尼尔机械纪元` | — |
| `others` | `Only Fans` / `OnlyFans` | `onlyfans` | — |

**归一化规则**：展示与筛选一律使用 `lowercase + 去除 '·' + 去除空白` 作为匹配键；**显示时保留首次出现时的原始写法**（`NIKKE` 保留全大写，因为它是官方写法），匹配时才用归一化键。这样既不出现重复筛选项，又不破坏品牌大小写。

**⚠ 规则四：`times` 类格式混乱，不可作为时间轴直接渲染**

实测 `times` 的 197 个值里有 **4 种不同格式**（`YY年M月` 91 个、`YYYY年M月` 40 个、`M月` 2 个、其余 64 个非日期如 `2026-03` / `2026.06` / `2023.4-20` / `Tier` / `Part 2` / `计划A`）。

→ **时间维度不要用 `times` 字段**，改用两个可靠来源：
1. **拍摄年月**：从文件名 `YYYYMMDD` 前 8 位解析（5,292/5,292 套图全部可解析，覆盖 20240501–20261025）。这是唯一可信的时间轴。
2. **套图来源年份**：`times` 里能识别为日期的才纳入（需先正则过滤掉 `Tier`/`Part 2`/`计划A` 这类非日期），且**必须归一化到 `YYYY-MM`** 再参与筛选。

→ 因此**卡片第二行不显示 `times`**，只显示实测拍摄日期。

| 参数 | 值 |

| 列数 | ≥1440: 6 · 1100–1439: 5 · 860–1099: 4 · 620–859: 3 · 400–619: 2 · <400: 1 |

| 纵向间距 | 32px（大于横向，用视觉把卡片与其下方的索引卡绑成一组） |
| 封面比例 | `aspect-ratio: 3 / 4`（0.75） |

**单套图内浏览（Level B，详情页）**

| 参数 | 值 |
|---|---|
| 布局 | 瀑布流，列宽自适应 200–320px，间距 16px |
| 单元比例 | **按图片原生比例，不裁切**（`width:100%; height:auto`） |
| 理由 | 21.3% 的横构图必须完整可见，裁切会切掉人物 |
| 单元间距 | 16px 横向 / 16px 纵向 |
| 单元圆角 | 8px |

### 5.2 封面选取与裁切规则（针对 77.9/21.3/0.8 的构成）

封面不是「第一张图」，而是：

1. 在套图内按文件名日期升序取前若干张（≤6 张）；
2. 优先选**比例 ≤ 0.80**（竖构图或方形）的图——77.9% 的素材满足；
3. 若该套图**全部为横构图**（约 21% 的可能性），取第一张，`object-position: 50% 35%`（人物通常上重）裁为 3:4；
4. `object-fit: cover` + `object-position: 50% 28%`（竖构图时人物头部保留优先）。

### 5.3 圆角一致性规则

| 层级 | 圆角 | 规则 |
|---|---|---|
| 图片本体 / 缩略图 | **8px** | 唯一的媒体圆角 |
| **裁切图片的父容器** | **8px** | **父容器圆角必须等于被裁切图片的圆角**。若卡片圆角为 8 而图片为 4，会在四角出现 4px 的「月牙」错位 |
| 按钮 / 输入框 / 分面行 | 6px | 交互控件统一 6px |
| 筛选胶囊（可点） | 999px | 全圆角，仅用于可点的胶囊 |
| 静态标签片（不可点） | 4px | 矩形片，读作「数据」而非「按钮」 |
| 头像 | 50% | 圆形 |
| 灯箱内的图 | **0px** | 全屏看图不该有圆角，图片本身成为唯一形状 |

### 5.4 遮罩与渐变叠加

**图上放文字的遮罩（唯一允许的渐变之一）：**

```
linear-gradient(to top,
  rgba(8,9,11,0.88) 0%,
  rgba(8,9,11,0.72) 18%,
  rgba(8,9,11,0.36) 42%,
  rgba(8,9,11,0.00) 68%)
```

- 从底部起 68% 高度内渐变，顶部 32% 完全透明，不遮挡人物面部区域。
- 文字颜色固定 `#F2F3F5`。实测在遮罩 88% 强度下，叠加**任何**底图（从 `#333333` 到 `#999999`）文字对比度仍 ≥ 15.69，恒定可读。
- 遮罩**只在需要放文字时叠加**（hover 态、灯箱内标题）。常态下的图片不加任何滤镜——`filter: brightness()` 一律不用，会篡改素材真实色彩。

**灯箱渐晕**：`radial-gradient(ellipse at center, rgba(8,9,11,0) 40%, rgba(8,9,11,0.55) 100%)`，仅用于灯箱背景层。

### 5.5 图片三态

| 状态 | 图片处理 | 其他 |
|---|---|---|
| **默认** | 无变换；1px 内描边 `inset 0 0 0 1px rgba(255,255,255,0.08)` | 卡片边 `--border-subtle` |
| **Hover** | `transform: scale(1.03)`，`transition: transform 240ms cubic-bezier(0.2,0,0,1)`；叠加底部遮罩渐变淡入（`opacity 0→1`，140ms），露出标题 | 卡片边 → `--border-strong`；加 `--shadow-1`；右上出现快捷操作组（收藏 ★ / 打开 ⤢），28px 命中区 |
| **Selected** | 2px `--accent` 内描边（`inset 0 0 0 2px #4FB3C4`）+ `filter: brightness(0.85)` 压暗，让选中项从密集墙中「沉」出来 | 右上角 20px 实心圆勾（`--accent` 底 + `--accent-ink` 对勾） |
| **Focus-visible** | **双层环**：外 `outline: 2px solid #6FC7D6; outline-offset: 2px`，内 `inset 0 0 0 1px rgba(14,15,18,0.9)`。单层描边在亮照片上会消失，双层保证在明暗两种素材上都可见 | 焦点环对 `--bg-base` CR 9.87，对 `--surface-2` CR 8.46 |

**Selected 的语义**：多选模式下的选中 = 图片压暗 + 强调色内框；**过滤命中的高亮** ≠ 选中，用「左侧 2px 强调色竖条 + 标题变 `--accent-hover`」表示，两者不混淆。

### 5.6 加载态（三级瀑布，不使用灰色骨架占位图）

图片占位**绝不能**是灰色方块——在一面照片墙里，一块灰方比一张慢加载的照片刺眼得多。

| 级 | 时机 | 表现 |
|---|---|---|
| **L1 主色块** | t=0，来自索引 | 图片容器显示该图的**预计算主色**（8×8 缩略取众数色），占位尺寸由 `aspect-ratio` 预留，**零布局抖动** |
| **L2 模糊占位（LQIP）** | t≈30ms | 主色块上叠 24px 宽的 base64 缩略图，`filter: blur(14px) saturate(1.1) scale(1.06)`，`transition: opacity 160ms` 淡入 |
| **L3 完整缩略图** | 解码完成 | 240px 缩略图淡入 200ms，移除 L2 |

- **骨架屏只用于文本/索引行**（首次索引查询 < 400ms 时）：2 条灰条（高 12px 宽 60%、高 10px 宽 40%）配 shimmer 扫光 `linear-gradient(100deg, rgba(255,255,255,0.04) 30%, rgba(255,255,255,0.09) 50%, rgba(255,255,255,0.04) 70%)`，1.6s 无限循环。
- **加载优先级**：索引 → 封面缩略图（可见区 + `rootMargin: 400px`）→ 详情页原图（853×1280 / 1280×853，本地读取，p50 仅 129KB，无需额外分片）。

## 7. 细节质感

### 7.1 阴影层级

暗色界面上阴影几乎不可见，**分层主要靠表面明度阶梯**（L 3.7% → 9.6% → 13.1% → 16.7%），阴影只用于真正「浮起来」的层。

| Token | 值 | 用在哪 |
|---|---|---|
| `--shadow-1` | `0 2px 8px rgba(0,0,0,0.40)` | 卡片 hover、悬浮快捷操作组 |
| `--shadow-2` | `0 8px 24px rgba(0,0,0,0.52), 0 1px 2px rgba(0,0,0,0.40)` | 下拉菜单、排序面板 |
| `--shadow-3` | `0 -12px 40px rgba(0,0,0,0.55)`（桌面 `-12px 0 40px`） | 详情抽屉 |
| `--shadow-4` | `0 16px 48px rgba(0,0,0,0.60)` | 灯箱 chrome、模态 |

- 浅色主题下阴影需要重新定义（深底不可见），用 `0 1px 2px rgba(20,25,35,0.06)` / `0 8px 24px rgba(20,25,35,0.10)` / `0 16px 48px rgba(20,25,35,0.14)`，并**加强 1px 边框**到 `rgba(0,0,0,0.12)`。

### 7.2 1px 边框的处理

- 边框颜色只有三档：`0.06` / `0.10` / `0.18` 白（暗色主题）。不要出现第四档。
- **每张图片必须有 1px 内描边** `inset 0 0 0 1px rgba(255,255,255,0.08)`。这不是装饰——实测 **5.0%** 的图片其 6px 边框近黑（边缘亮度 p05 = 0.139），没有内描边它们会在深底上「消失」，照片墙会碎成一片没有边界的光斑。
- 描边用 `box-shadow: inset` 而非 `border`，避免占位、避免改变尺寸。
- 卡片边框用真实 `border: 1px`，因为卡片尺寸需要稳定。

### 7.3 玻璃拟态（backdrop-filter）：**不用**

结论：**全站禁用 `backdrop-filter`。**

理由：
1. **对比度不可控。** 顶栏浮在照片墙上方时，背景亮度在 0.14–0.81 之间跳变（图片边缘亮度实测分布），任何半透明背景都无法保证文字对比度。改为**实色** `--surface-1` 顶栏 + 1px 下边框，语义清晰且永远可读。
2. **会污染界面色彩。** 毛玻璃会把身后照片的色彩渗进 UI，破坏 §2.4 建立的「冷界面 / 暖内容」分离。
3. **性能。** 5,292 张卡的滚动页面上叠 backdrop-filter，等于每帧重算背景模糊。
4. **暗房隐喻不需要它。** 暗房是暗的、实的、确定的，不是折射的。

唯一例外：**没有**。灯箱顶/底栏也是实色 `rgba(8,9,11,0.86)`。

### 7.4 渐变用在哪

只有三处：

| 位置 | 渐变 | 目的 |
|---|---|---|
| 图片上的文字遮罩 | §5.4 的底部渐变 | 保证图上文字在任何素材上可读（实测 ≥15.69 CR） |
| 灯箱背景 | 径向渐晕 `rgba(8,9,11,0)→0.55` | 把视线收进中央的图 |
| 骨架屏 shimmer | `rgba(255,255,255,0.04)→0.09→0.04` 100° | 表达加载中 |

**禁止**：按钮渐变、卡片渐变、导航栏渐变、任何「彩色光晕 / aurora blob」装饰、强调色渐变。

### 7.5 图片圆角与卡片圆角的一致性规则

> **裁切图片的父容器圆角 = 图片圆角 = 8px。**

- 二者必须相等。任何「卡片 8px / 图 4px」的组合会在四角留下月牙状错位，在密集网格中非常显眼。
- 缩略图网格、封面、胶片条单元、灯箱缩略图：**一律 8px**。
- 灯箱主图：**0px**（全屏无框）。
- 头像：50%。

### 7.8 敏感内容处理（素材含 NSFW 目录）

根目录名为 `cosplay 写真[NSFW]`，且存在带 `NSFW` 字样的目录名。界面必须提供：

- 全局开关「**模糊敏感内容**」，默认**开**（针对 NSFW 根目录）。
- 生效方式：封面 `filter: blur(18px)` + 叠一层 `--bg-void` 40% + 中央 12px 胶囊「点击显示」（`--text-secondary` 底 `rgba(8,9,11,0.7)`）。
- Hover / focus 时解除模糊（160ms 过渡）。
- 状态持久化到 localStorage。
- 该开关的位置：筛选侧栏顶部，**独立于普通分面**，用 `--danger` 色的小标记区分（不是红色按钮，只是 6px 圆点 + 12px 文字）。

## 8. 暗色 / 浅色双模

| | 暗色（默认） | 浅色 |
|---|---|---|
| 页面底 | `#0E0F12` | `#F2F3F5` |
| 卡片面 | `#16171B` | `#FFFFFF` |
| 交互面 | `#1E1F25` | `#F7F8F9` |
| 强调色 | `#4FB3C4` | `#1F7A8A` |
| 强调色上文字 | `#0B0C0E` | `#FFFFFF` |
| 档案章 | `#D9A441` | `#8A6114` |
| 主文字 | `#F2F3F5` | `#14161A` |
| 分层靠 | 表面明度阶梯 + 边框 | **边框 + 阴影**（浅底上明度阶梯不可用） |

### 默认走暗色，理由（量化）

1. **明度层级不能反。** 图片中位亮度 0.527，95 分位 0.763。若界面用浅底（`#F2F3F5`，相对亮度 Y=0.8957），页面会比**中位照片亮 1.7 倍**、比 95 分位照片还亮 —— 页面成为画面上最亮的东西，照片反而成了「暗洞」，图与界面关系颠倒。暗底（`#0E0F12`，Y=0.0048）下最亮的 UI 表面也只有 Y=0.0208，比最暗的 5% 图片还暗 10.4 倍，照片才是发光体。
2. **素材 67.7% 的图片平均饱和度 < 0.15。** 这类低饱和图在白底上会进一步「发灰」，失去层次。深底给低饱和素材更多对比余量。
3. **暗房隐喻的一致性。** 看照片的场景本身是低照度环境（卧室/深夜），浅色界面在暗环境下会产生刺眼的光晕。
4. **边缘可控性。** 实测 5.0% 的图片边框近黑（边缘亮度 p05 = 0.139）。深底 + 1px 内描边可以救回这批图的轮廓；浅底上这批图会变成「白底上的白块」，同样丢失边界——但深底方案已被验证有效。

浅色模式**必须提供**（部分用户在白天/亮环境下需要），且必须用同一套语义 token 换值，切换时**不改变布局、不改变圆角、不改变间距**。浅色模式下的补偿措施：卡片边框加强到 `rgba(0,0,0,0.12)`，阴影使用 §7.1 的浅色版本。

## 9. 禁用清单（3 条）

### ① 禁止纯黑背景 `#000000`

**原因（实测）**：素材里 **5.0%** 的图片其 6px 边框区域亮度 < 0.139，且单图平均亮度 p05 = 0.217。在 `#000` 上，这批图的轮廓会彻底消失，照片墙碎成一片无边界的光斑，视觉上像「加载失败的空隙」而不是照片。同时 `#000` 与 `#FFF` 并置会造成极强眩光。

**替代**：`--bg-base: #0E0F12`（带 12.5% 冷饱和，不是死黑），**且每张图片加 1px `rgba(255,255,255,0.08)` 内描边**——这一条是必需的，不是锦上添花。

### ② 禁止霓虹紫 / 赛博粉紫渐变（及任何饱和度 > 60% 的界面强调色）

**原因（实测）**：素材的高饱和像素里橙占 41.1%、红占 25.3%（合计 66.4%）。紫调界面在暗底上会立刻把观感带向「游戏 CG / 赛博」，与「本地写真归档」的属性不符；同时紫/品红在真实照片里又常常出现（妆造、灯光、滤镜），UI 与照片会争夺同一批色彩注意力。而且这类配色是模板化产物，与「暗房档案柜」的主张直接矛盾。

**替代**：单一冷青蓝强调 `#4FB3C4`（H188.7 S49.8% L53.9%）——这个色相在素材里只占 3.3%，是素材中最稀缺的色相，所以永远不会被误认成照片内容。界面中性色全部压在 S ≤ 15.8% 的冷灰区间。饱和度上限写死在 §2.3 第 4 条。

### ③ 禁止在图片上直接叠加标题文字 / 用大圆角卡片 + 阴影做「现代作品集」模板

**原因（实测 + 结构）**：
- 素材构成是 77.9% 竖构图、21.3% 横构图、仅 0.8% 方形，且 EXIF **完全缺失**——元数据 100% 来自文件名与目录名。这意味着「图片上叠大字标题」的 Instagram/Pinterest 式卡片在此**不可行**：文字压在人物主体上，而素材里大量是近景半身与特写，任何覆盖都会压住脸。且目录名里的中文标签（2,794 个长尾 `others` 值）需要 11.5px 字号才读得清，放在 249px 宽的图上叠 20px 标题会直接溢出。
- 「大圆角（16px+）+ 柔和投影 + 卡片浮起」是通用 SaaS 模板语言，与本产品的「工具感、档案感」冲突。

**替代**：
- 元数据全部放在**图片下方独立的索引卡区**，用 §4.4 的三层结构（coser 胶囊 / 标题 / 档案章+标签行）。
- 圆角上限 **8px**，阴影只用于真正浮起的层（抽屉、下拉、灯箱），卡片默认无阴影。
- 若确实需要图上文字（如灯箱内标题），使用 §5.4 的实测安全遮罩，绝不在图上居中放大字。
