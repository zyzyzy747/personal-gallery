## 二、必须守住的目录契约

1. **两层不可多加一层**：`01-图库\<分组>\<套图>\<文件>`。
   `build.py` 的 `scan()` 只往下走两级：分组名进索引的 `group` 字段，
   套图目录名才是元数据来源（`#coser - #作品 #角色`）。多嵌一层，
   整组会变成一个「套图」，里面几百张图挤成一张卡。
2. **分组名里带 `[NSFW]`** → 前端 `isNSFW` 打码。改名时别丢。
3. **分组名里带「漫画/同人/画集/CG集/插画/comic」** → 索引标 `manga`，
   前端单独成模块。`媚黑漫画库` 的「漫画」二字是功能性的。
4. **分类 = `02-小说\` 的一级子目录**，新增分类只要新建目录，不改代码。

## 三、junction 为什么留着

- 8777 上的 `serve.py` 是整理前启动的 SYSTEM 会话孤儿进程，普通权限停不掉，
  它把旧 `RAW_ROOTS` / `novel_roots` 读进了内存。junction 让旧进程在重启前
  继续按旧路径读到文件，页面不会整体 404。
- `E:\Download\novel_download` 下有 60 多个爬虫脚本把旧路径写死，
  junction 让它们不用逐个改。

服务重启（重启电脑或管理员 `taskkill`）之后，两个 junction 都可以删：

```cmd
rmdir "E:\Download\Telegram"
rmdir "E:\Download\novel_download"
```

删之前确认 `serve.py` 进程确实是重启后的新进程（`netstat -ano | findstr :8777`
拿 PID，再对 `Get-Process -Id <PID> | Select StartTime`，启动时间要晚于整理时间）。

## 四、索引 id 的稳定化处理

`build.py` 的 `load_id_map()` 用 `path → id` 沿用旧 id，缩略图文件名是
`t<slug(id)>.jpg`。目录一改名，path 全变 → 7,675 套会被当成全新套图重新
分配 id → 缩略图全部重生成。

所以整理当天先跑了一个**索引 path 重映射**脚本（一次性，无留存价值）：

1. 备份 `index.final.json`；
2. 把每套的 `path` / `vkey` 按「旧分组前缀 → 新分组前缀」替换，`group` 换成新名；
3. 删掉旧的 `index.final.json.gz`（否则服务端优先发 gz，浏览器继续拿旧路径）；
4. 再跑 `build.py` 增量 → 只重建「文件清单变了」的 3,754 个分片。

结果：**7,675 套原始 id 全部沿用**，只有 76 个散图虚拟套图因旧索引里没有
`vkey`（同一分组根共享一个 path）重新分配了 id，多生成 76 张封面，无视觉影响。

## 五、电子书入库

`NOVEL_EXT` 从 `('.txt',)` 扩成：

```python
NOVEL_TEXT_EXT   = ('.txt',)
NOVEL_EBOOK_EXT  = ('.epub', '.mobi', '.azw3', '.chm', '.pdf', '.doc', '.docx')
NOVEL_EXT        = NOVEL_TEXT_EXT + NOVEL_EBOOK_EXT
NOVEL_READABLE_EXT = ('.txt', '.epub')
```

- 每条小说带 `f` 字段（格式）。旧数据没有 `f`，前端按 `txt` 处理。
- epub 字数用 **`zipfile.ZipInfo.file_size` 之和 / 3** 估算（解压后体积，
  不读内容）；mobi/chm/pdf 没有通用解压信息，字数显示 `—`。
- 在线阅读：`serve.py` 的 `read_epub_text()` 解析 `container.xml` → OPF →
  `<spine>` 顺序拼 xhtml，正则去标签，全标准库实现。
- 非 txt/epub 格式，前端点击直接走 `/novel/<p>` 下载，不进阅读器。
