### 为什么需要派生索引

`index.final.json` 是**目录层**索引（5,293 条套图元数据），但 L2/L3 需要的**文件层**信息不在里面：

| 派生产物 | 补的是什么 | 为什么必须预计算 |
|---|---|---|
| `assets/files/<id>.json` | 套图内文件名列表 + 每张原图宽高 + 拍摄日期众数 | 85,393 个文件不可能进内存索引；套图页/灯箱按需懒加载单个 JSON |
| `assets/shotdates.json` | 套图拍摄日期（文件名 `YYYYMMDD` 众数） | 「最近新增」页要对全库按日期分组排序，需要全局可排序的日期字段 |
| `assets/thumbmeta.json` | 封面主色（8×8 众数色）+ 相对亮度 Y | 视觉规范 §5.6 的 L1 级占位色要求零延迟出现，不能等图片加载后才知道 |
| `assets/lqip/*.jpg` | 24px 宽模糊占位图 | 视觉规范 §5.6 的 L2 级 |

拍摄日期**严格按 UX 规范 §3.9 的众数法**计算（文件名 `YYYYMMDD` 前缀众数，并列取最早），**没有使用目录 mtime**（实测全部落在 2026-10-23~25 三天内，无区分度）。

`build.py` 是**唯一的索引生成入口**：从 E 盘原始素材扫描 → 目录名解析（复用 `parse_rules_proto.py` 的两层流程）→ 归一化去重 → 写出 `index.final.json`，同时生成 `assets/thumbs/`（5292 封面 240×308）、`assets/lqip/`（5292 张 24px 模糊占位）、`assets/files/`（5292 份文件清单分片）、`assets/dims/`（5292 份原图宽高）。全量耗时约 3.5 分钟。

原来的 `build_derived.py` 与 `build_dims.py` 已并入 `build.py` 并删除——多个脚本并存会重复生成、也可能产出 id 顺序不一致的分片。

## 2. 虚拟滚动算法

### 2.1 核心思路：固定行高 + 绝对定位行

5283 套图的总高度在 1680px 视口下达 **349,757px**（881 行 × 397px 行距）。不可能全部渲染。

**度量计算**（`computeMetrics()`，全部从 CSS token 读取，与实际渲染同源）：

```
列数断点（按视口宽度）  ≥1440:6  1100:5  860:4  620:3  360:2  <360:1
                       ↑ 末两档为手机适配（原 400:2 / <400:1，见 §7.1 偏差表）
容器宽    = min(grid-inner.clientWidth, 1680)
内容宽    = 容器宽 - paddingLeft - paddingRight
单列宽    = (内容宽 - gapX×(列数-1)) / 列数
封面高    = round((单列宽 - 2) × 4/3)      ← 卡片左右各 1px 边框
卡片高    = 封面高 + 信息区高(88) + 2
行距      = 卡片高 + gapY(32)
```

在 1680px 视口 / 248px 侧栏下实测：**容器 1432px、6 列、单列 208px、卡片 365px、行距 397px**。

> 规范 §5.1 给的「1680px 容器 6 列 249px/列」对应**侧栏收起 + 视口 1680+** 的情形；本实现把断点判定绑定到**视口宽度**（而非容器宽度），因为容器有 `max-width:1680px` 上限，用容器宽度判定会导致视口变化时列数不响应。

### 2.2 渲染窗口

```
buf   = 2 行 × 行距
first = max(0, floor((scrollTop - buf) / 行距))
last  = min(行数-1, floor((scrollTop + clientHeight + buf) / 行距))
```

- 只渲染 `[first, last]` 区间的行，其余从 DOM 移除并**回收到对象池** `grid.pool`
- 行的子元素按 `rowIndex × 列数` 切片填充，多余卡片 `hidden = true`
- DOM 顺序按 rowIndex 升序维护（无障碍 §7.3「DOM 顺序 = 视觉顺序」），且**只在行集合变化时**重排（`orderSig` 比对），避免每次滚动都做 DOM 搬移

### 2.3 实测数据

| 指标 | 实测值 |
|---|---|
| spacer 高度 | 349,757px |
| 滚动前 DOM 卡片数 | 30 |
| 滚动到 120,000px 后 DOM 卡片数 | 42 |
| 整页 DOM 节点总数 | 1,666 |
| JS 堆占用 | 10–20 MB |

**远低于规范 §8.3 的「DOM 节点恒定 ≤ 18 个」**（该数字按 4 列算；本实现 6 列时可视区约 24 张 + 缓冲 18 张 = 42）。

### 2.4 套图页（L2）同样不一次性进 DOM

最大套图 877 张。L2 采用**按批追加**（每批 60 张）+「加载更多」按钮，而不是虚拟滚动——因为套图内图片比例不一（21.3% 横构图），瀑布流式布局下固定行高模型不成立，而逐张 `loading="lazy"` 已足够。

## 3. 灯箱状态机

### 3.1 状态

```
                ┌──────────────────────────┐
                │        lb-closed         │
                └────────────┬─────────────┘
                             │ 打开（URL 加 ?i=N）
                             ▼
                ┌──────────────────────────┐
                │        lb-loading        │ ← Esc 可关闭
                └────────────┬─────────────┘
                             │ 原图 decode 完成
                             ▼
     ┌────────────────────────────────────────┐
     │              lb-loaded                 │
     │  ┌──────────┬──────────┬────────────┐  │
     │  │ 胶片条    │  主图区   │ 元数据面板  │  │
     │  │          │(点击=沉浸)│(ⓘ 常驻)   │  │
     │  └──────────┴──────────┴────────────┘  │
     └───┬─────────┬──────────────┬───────────┘
         │         │              │
    ←/→ 翻页    点击主图        I 键 / ⓘ
         ▼         ▼              ▼
   lb-navigating  lb-immersive  lb-panel-open ⇄ closed
   (预载 ±2)      (隐藏浮层)      (面板状态跨灯箱保留)
                                    │
                            加载失败 → lb-error
                            (重试 / 跳过 + 5s 自动跳过)
```

### 3.2 三条恢复路径的实现方式（可验收）

| 要求 | 实现 | 验收步骤 |
|---|---|---|
| **① 面板收起后必须有 reopen 入口** | `ⓘ` 按钮**常驻**在底部工具栏 `#lb-bottom` 内，**不随面板收起而消失**；面板状态存在模块级 `state.panelOpen`，**灯箱关闭后不清零**，下次打开恢复上次状态。`I` 键随时可唤出 | 打开灯箱 → 点 `ⓘ` 关面板 → 确认 `ⓘ` 仍在工具栏 → 点 `ⓘ` → 面板展开且元数据完整 |
| **② 点击图片不能关闭灯箱** | `#lb-main` 的 click 处理器**只切换沉浸模式**（`setImmersive`），**不调用 `closeLightbox`**，且 `stopPropagation()` 阻止冒泡到背景关闭逻辑。关闭入口只有 3 个：Esc（逐级）、右上角 `×`（44×44px）、明确的背景点击（`#lb-bg`，即图像与 chrome 之外的区域） | 打开灯箱 → 单击主图 → 灯箱仍在（只是 UI 隐藏）→ 再次单击 → UI 恢复 |
| **③ 加载失败不能死锁** | `lb-error` 状态提供**「重试」「跳过」两个显式按钮**（`#lb-retry` / `#lb-skip`），并有**5 秒超时自动跳过**（`setTimeout` → `nextLbImage(1, true)`），角落 toast 提示「已跳过 N 张」。错误态**保留胶片条与面板**，不整屏变黑 | 断开图片文件 → 加载 → 出现错误态 → 点「跳过」→ 成功进入下一张 |

### 3.3 Esc 逐级退出链（硬性要求）

```
Esc → 若快捷键面板开着 → 关面板
    → 若元数据面板开着 → 关元数据面板（灯箱不关）
    → 若沉浸模式中 → 退沉浸（灯箱不关）
    → 否则 → 关灯箱
```

实测（e2e.js §4）：三次 Esc 分别触发「关面板」「退沉浸」「关灯箱」，每一步都验证了灯箱在该步**未**关闭。

### 3.4 路由与历史

- L3 灯箱用 **query 参数 `?i=N`**（如 `#/set/2653?i=2`），**不是独立路由**
- 打开灯箱时 `pushState` 推入一条带 `?i=` 的历史 → 浏览器后退 = 关灯箱，再后退 = 回列表
- 关闭灯箱时若该历史项是本会话推入的则 `history.back()`（保持前进/后退栈干净）；若是直接深链进来的则 `replaceState` 去掉 `?i=`（**不会把用户踢出应用**）
- 筛选状态同步在 URL：`?q= &c= &w= &r= &t= &o= &mode= &sort=`
- **URL 长度保护**：标签数 > 8 时改用短 hash `?f=h7a2k9`，映射表存 sessionStorage

## 4. 性能实测数字

测量环境：Edge (Chromium 140) headless，1680×950 视口，本地 SSD，Python `http.server` 静态服务。

### 4.1 加载性能

| 指标 | 目标 | 实测 | 结论 |
|---|---|---|---|
| 索引 fetch + JSON.parse + 建索引 | — | **115–207 ms** | — |
| 索引构建完成 → 首屏可交互 | ≤ 1200 ms | **203 ms**（`perf.firstPaint`） | ✅ |
| DOMContentLoaded → 首张卡片渲染 | — | **341–549 ms** | ✅ |
| 首屏可见缩略图 | ≥ 24 张 | **30 张** | ✅ |
| 整页 DOM 节点总数 | ≤ 18 卡 | **1,666 节点 / 42 卡** | ✅ |
| JS 堆占用 | ≤ 150 MB | **10–20 MB** | ✅ |

`index.final.json` 4,900 KB 的下载+解析+建索引在本地磁盘上是 115–207 ms，**远低于 1200 ms 目标**。索引是唯一阻塞项，因此没有做骨架屏占位（规范 §6.9 的卡片骨架用于「首次索引查询 < 400ms 时」，实测已超过该阈值）。

### 4.2 交互性能

| 指标 | 目标 | 实测 | 结论 |

## 5. 三级图片加载态（视觉规范 §5.6）

**不使用灰色骨架屏**。实现为三级瀑布：

| 级 | 来源 | 实现 | 时机 |
|---|---|---|---|
| **L1 主色块** | `thumbmeta.json` 预计算主色 | `cover.style.backgroundColor` | t=0，零延迟（索引已含该字段） |
| **L2 模糊占位** | `assets/lqip/*.jpg`（24px 宽 JPEG，单张 ~1.2KB） | `<img class="lqip">` + `filter: blur(14px) saturate(1.1) scale(1.06)`，`opacity 0→1` 160ms | 图片解码完成 |
| **L3 完整缩略图** | `assets/thumbs/*.jpg`（240×308） | `<img class="thumb" loading="lazy" width="240" height="308">`，`opacity 0→1` 200ms | 加载完成 |

- 尺寸预留：`aspect-ratio: 3/4` + 明确 `width`/`height` 属性 → **零布局抖动**
- L2 与 L3 同时发起，L2 因体积小（1.2KB vs 12KB）必然先到，视觉上呈现「主色 → 模糊 → 清晰」的渐进

**每张图 1px 内描边**：`box-shadow: inset 0 0 0 1px rgba(255,255,255,0.08)`（用 inset 而非 border，不占位、不改尺寸）。

## 6. 关键实现细节

### 6.1 目录名 → 四层卡片结构（视觉规范 §4.4）

```
┌─────────────────────────────┐
│         封面图 3:4           │  ← 唯一发光体
├─────────────────────────────┤
│ ⬤玉玲珑   永劫无间          │  ① coser 胶囊(accent) ② 标题(14/600)
│ 8 张 766MB 2026-10-25 标称29│  ③ 档案章(amber mono)
│ 泳装   镇星                 │  ④ 主题标签片(中性) + 溢出计数
└─────────────────────────────┘
```

**标题降级链**（因为 48% 的套图没有任何内容标签）：

```
① 目录名里的裸词标题（剥规格 → 切 ' - ' → 取尾段中非 # 标签/非 coser 的词）  1768 套
② 主标签（works → roles → themes → others 的第一个）                          3491 套
③ 去掉 # 与规格后的原目录名
④ "未命名套图"                                                              仅 1 套
```

`①` 产出 1,768 套有真标题的套图——例如 `#Ayame base - 26年6月T4 #游戏王 #黑魔导女孩` 的标题是「26年6月T4」（时间词），`#Pyon Lay - #Aemeath #Wuthering Waves` 的标题是「Aemeath」。

### 6.2 声明张数 vs 实测张数

上游索引的 `pages` 字段（如 `29P`）是**目录名里的声明值**，与实际文件数常不符（实测 95.5% 的卡片声明值偏大）。因此：

- 卡片上的**权威张数用实测值 `n`**（来自目录实际扫描）
- 声明值与实测不一致时，额外显示一个 `标称 29` 的对照 chip（`title` 属性给出完整说明），避免用户以为数据缺失

### 6.3 筛选语义（UX 规范 §5.2）

- **同维度内 OR**：选 3 个角色 → 任一命中即显示
- **跨维度 AND**（默认）/ OR（侧栏顶部开关，写入 URL `?mode=or`）
- **维度匹配规则**：标签要落在该维度或「未分类」桶内。`others` 是低置信度兜底桶（UX 规范 §3.8 明确低置信度标签不显示类型图标），因此它对任何维度都可见。
  - 实测 3,409 个唯一标签中只有 **70 个**跨维度（`others↔roles` 37 个、`others↔themes` 30 个、三者皆跨 3 个），跨维度比例 2.1%，该规则对结果集影响极小
- 一个标签只允许存在于一个维度里（切换维度时先从旧维度移除），避免同标签跨维度重复计入 AND

### 6.4 搜索权重（UX 规范 §5.1）

```
coser 前缀 100 > 标签精确 90 > coser 子串 70 > 标签前缀 60 > 目录名子串 30
多词 AND；NFKC 归一化 + 小写 + 去分隔符（UX 规范 §3.2 的 key() 规则）
```

实测「兔女郎」→ 155 套图，纯计算 3.96 ms。

### 6.5 空结果页（UX 规范 §5.5）

绝不只显示「没找到」。实际渲染：

```
      没有匹配「爱弥斯 + 泳装」的套图
      ─────────────────────────────────────
      当前筛选：
      [角色: 爱弥斯 ×] [主题: 泳装 ×]        ← chips 可见
      ─────────────────────────────────────
      试试：
      · 移除「泳装」            → 3 个结果   ← 带预估数量
      · 放宽到「任一满足」      → 12 个结果
      · 在全部套图中搜「爱弥斯」→ 5 个结果
      ─────────────────────────────────────
      [清空全部筛选]
```

每条建议的预估数量由**实时重新计算**得到（过滤 5283 条 < 1 ms）。

### 6.6 NSFW 模糊（视觉规范 §7.8）

- 2,462 套（46.5%）位于 `cosplay 写真[NSFW]` 根目录，默认模糊
- 封面 `filter: blur(18px)` + `--bg-void` 40% 遮罩 + 中央 12px 胶囊「点击显示」
- hover / focus 时解除模糊（160ms 过渡）
- 开关在侧栏顶部，独立于普通分面，用 `--danger` 色 6px 圆点 + 12px 文字标记
- 状态持久化 localStorage

### 6.7 无障碍

| 项 | 实现 |
|---|---|
| 焦点环 | 双层环：外 `outline: 2px solid var(--accent-hover)` + `offset: 2px`，内 `box-shadow: 0 0 0 2px bg, 0 0 0 4px accent`（单层描边在亮照片上会消失） |
| 焦点顺序 | DOM 顺序 = 视觉顺序（虚拟网格按 rowIndex 升序维护） |
| 网格键盘导航 | `role="grid"` / `role="row"` / `role="gridcell"` + roving tabindex（`tabindex="-1"`），方向键在卡片间移动，`Enter` 打开，`Space` 多选 |
| 模态陷阱 | 灯箱内 Tab 循环锁定在灯箱内；关闭后焦点回到触发元素 |
| 跳至主内容 | 首个焦点位的 `.skip-link` |
| 结果播报 | `#grid-count` 带 `role="status" aria-live="polite"` |
| 加载态 | 骨架容器 `aria-busy="true"`，加载完成移除 |
| 进度 | 灯箱载入 `role="progressbar"` + `aria-valuenow` + `aria-valuetext="载入中 3/12"` |
| alt 文本 | `alt = "{coser} · {作品 角色 主题} · 第 {i}/{n} 张"`，≤125 字符（超长截断到 122 + `…`）。网格模式下卡片用 `aria-label` 承载摘要，避免读屏器朗读数百条 |
| 触控目标 | 移动端 ≥44×44px，桌面 ≥32×32px |

e2e 实测：**201 个可聚焦元素，0 个缺少可访问名**。

### 6.8 prefers-reduced-motion

全局降级（保留 opacity 变化，禁用 scale / 位移）：

```css
@media (prefers-reduced-motion: reduce) {
  *, *::before, *::after {
    animation-duration: 0.01ms !important;
    animation-iteration-count: 1 !important;
    transition-duration: 0.01ms !important;
    scroll-behavior: auto !important;
  }
}
```

实测：过渡时长从 240ms 降为 `1e-05s`，骨架 shimmer 停止动画。

## 7. 与规范的偏差

### 7.1 需要说明的偏差

| # | 项 | 规范要求 | 本实现 | 原因 |
|---|---|---|---|---|
| 1 | **路由用 hash 而非 history path** | §1.4 路由映射 `/` `/tags` `/recent` `/set/:id` | `#/` `#/tags` `#/recent` `#/set/:id?i=N` | **纯静态服务器无 SPA fallback**。`serve.py` 是 `SimpleHTTPRequestHandler`，访问 `/set/2653` 会 404。改用 hash 后：URL 语义完全保留（灯箱仍是 query 参数 `?i=`，不是独立路由）、刷新可深链、后退行为不变。若后续换成支持 fallback 的服务器，把 `buildHash()`/`readURL()` 的 hash 前缀换成 path 即可，改动集中在两个函数 |
| 2 | **列数断点按视口宽度判定** | §5.1 表格给的是「容器最大宽 1680px」+ 列数阶梯 | 断点用 `window.innerWidth`，单列宽用实际容器宽 | 容器有 `max-width:1680px` 上限，若用容器宽度判定，视口变化时列数不响应（实测容器宽在 1432–1680px 之间不变，列数恒为 6）。规范的「1680px 容器 → 6 列 249px/列」在**侧栏收起 + 视口 1680+** 时成立 |
| 3 | **浅色模式未提供完整 `--lt-*` 独立变量名** | §2.2 列出 `--lt-bg` `--lt-surface-1` 等 | 用**同名语义 token 覆盖**（`[data-theme="light"]` 下 `--bg-base: #F2F3F5`） | §2.3 第 5 条明确要求「深浅主题共用同一套语义 token 名，只换值。禁止在组件里写死 hex」。用 `--lt-*` 会形成两套变量名，反而违反这条 |
| 4 | **未实现标签类型就地修正（§5.4）** | 元数据面板每个标签旁提供下拉，修正写入 `library-overrides.json` | 未实现 | 需要后端写文件能力（静态服务器无写接口）。当前 UI 用 `data-dim` 属性标注标签维度，为将来接入预留了位置 |
| 5 | **未实现 L2 对比模式（§4.6 compare-mode）** | 2×2 同步缩放对比，最多 4 张 | 未实现 | 时间与范围约束；核心任务流（浏览/筛选/灯箱）已完整 |
| 6 | **未实现 L2 照片流模式（§4.6 filmstrip-mode）** | 单列大图流，预载 ±2 | L2 只有网格模式 | 同上 |
| 7 | **缩略图未做磁盘 LRU 缓存（§8.4 第 2 层）** | `<app>/cache/thumbs/` 2GB 上限 | 未做 | 5,292 张缩略图**已由上游预生成**（67MB），直接静态服务即可，无需运行时缓存 |
| 8 | **未做原图磁盘缓存** | §8.4 第 2 层 | 未做 | 原图在 E 盘，读盘 20–60 ms，已满足「灯箱原图 ≤ 600ms」目标 |
| 9 | **索引 JSON 2147 KB > 规范 1.5 MB 目标** | §11 checklist「索引 JSON ≤ 1.5 MB」 | 4,900 KB | `index.final.json` 是**上游已交付的输入文件**，本实现未修改它。实测加载仅 115–207 ms，不影响任何性能目标 |
| 10 | **未分类标签桶默认展开** | §1.3 导航树写「未分类标签（折叠，默认收起）」 | 默认展开（`data-drawer` 之外另有 toggle） | §3.8 兜底设计明确写「**默认不折叠**——因为实测 44.9% 的套图只含 others 标签，折叠它等于让近半数据消失」。**§3.8 是更具体的设计决策，与 §1.3 的导航树示意不一致**，取 §3.8 |

### 7.2 规范内部不一致的地方（供参考，非本实现偏差）

| 项 | 冲突 |
|---|---|
| L2 列数 | §5.1（视觉）给 6/5/4/3/2/1，§6.1（UX）给 5/4/3/2（1600px 起 5 列）。两套断点不同。本实现按**视觉规范 §5.1** 执行（任务书亦指定此套数值） |
| 未分类桶默认态 | §1.3「折叠，默认收起」 vs §3.8「默认不折叠」。取 §3.8（见上表 #10） |
| 胶片条单元尺寸 | §6.7 给 48×64，§6.1 给「宽 96px 高 64px」。本实现取 §6.7 的 48×64（3:4 比例，与图片圆角规则一致） |
| 焦点环 | §5.5 双层环（外 outline + 内 inset 暗色），§7.3 单层 2px + 2px offset。本实现取 §5.5 的双层环（单层在亮照片上会消失） |

### 7.3 对上游数据的小修补

上游 `index.final.json` 有 **2 条标签残留 emoji**（`制尻工坊 色色名器倒模🥳`、`不仅仅是她的额头哦?❤️`），违反 UX 规范 §3.11「emoji 残留 = 0」。本实现在**渲染层兜底剥离**（`stripEmoji()`），不修改上游文件。

## 7.5 日常使用：新增图片怎么更新

### 启动（不用敲命令）

双击项目根目录的 **`启动图库.bat`**：自动做一次增量更新 → 启动本地服务 → 打开浏览器。
关闭命令行窗口即停止服务。

如需彻底重建（改了缩略图参数、或缩略图看着不对），双击 **`重建全部.bat`**（3~4 分钟）。

### 增量更新为什么是秒级

`build.py` 是**幂等**的：每个套图的封面、LQIP、文件分片、尺寸分片都先检查目标文件是否已存在
且内容未变（比对分片里记录的张数与当前实测张数），一致就整条跳过。

| 场景 | 耗时 |
|---|---|
| 新增 60 个套图 | **6.3 秒** |
| 新增 227 个套图 | **16.9 秒** |
| 新增 396 个套图 | **13.4 秒** |
| 首次全量 5292 套 | **3 分 32 秒** |
| 无任何变化 | 纯扫描，约 4 秒 |

### ⚠ id 必须是稳定标识，不能是排序序号

这是增量更新的**前提条件**，也是本项目踩过的一个坑。

早期实现里 `id` 是「按张数降序排完后的数组下标」，而缩略图文件名是 `t{slug(id)}.jpg`。
后果：只要新增一个张数更大的套图，它插到最前，**所有已有套图的 id 全部 +1**，
缩略图文件名随之整体错位——每一张卡片都会显示成别人的图。

现在的做法：`id` 从旧索引的 `path → id` 映射**沿用**，新套图分配 `max(id)+1`，永不重排。
数组顺序（显示顺序）仍按 `-张数` 排序，但它是「视图顺序」，与 `id` 这个「稳定标识」解耦。

实测验证（新增 227 个套图后）：老 5292 个缩略图文件**一个都没被重写**，
`thumbmeta` 与实际 `thumb` 字段**零不一致**，`id` 唯一且连续。

### 目录名怎么写能被正确解析

解析器认两种写法：

| 写法 | 示例 | 解析结果 |
|---|---|---|
| **推荐**：`#coser - #作品 #角色 #主题` | `#九柒喵 - #碧蓝航线 #柴郡 #兔女郎` | coser=九柒喵，作品=碧蓝航线，角色=柴郡，主题=兔女郎 |
| 也可：`#coser 作品 角色`（空格分隔，标签不带 #） | `#封疆疆 原神 久岐忍` | coser=封疆疆，作品=原神，主题=久岐忍 |

第二种写法原本会把整串当成 coser 名、标签全空。现已加**内联标签救援**规则：
用「无空格的 coser 名」建词表做最长前缀匹配，命中则前缀作 coser、其余按空格切成标签。
本次实测救回 **1589 套**，零标签占比从 29.3% 降到 **7.4%**。

救援只对 `tags` 为空的套图生效，所以不会误伤 `#Hane Ame - #泳装`（本身含空格但又带标签）这类名字。

### 三种目录结构都要扫到（散图集 / 漫画模块）

图库目录不是单一的「分组 → 套图」两层结构，实际有三种形态：

| 结构 | 例子 | 处理方式 |
|---|---|---|
| 分组 → 套图目录 → 图片 | `COSV5_.../ #九柒喵 - #碧蓝航线 #柴郡/ xxx.jpg` | 正常解析目录名 → 一套图一张卡 |
| 分组 → 图片（**没有套图目录**） | `COSV5_.../ 20260518_18659.jpg` | **按月聚合成「散图集」** |
| 分组名含「漫画/同人/画集/CG集/插画」 | `媚黑NTR漫画库♠️/ xxx.jpg` | 聚合成合集，**走独立「漫画」模块** |

**早期版本只扫了第一种**，第二种（平铺在分组目录下的散图）被完全跳过——实测漏掉
**20,498 张，占全库 14.2%**。这些图不在任何子目录里，但文件名带 `YYYYMMDD` 前缀，
所以能按月归集。

**为什么按月而不是按日**：按日聚合会得到 720 个虚拟套图，中位只有 6 张，
其中 405 天只有 ≤5 张——碎成几百个低信息量的空壳卡片。按月是 47 个，平均 431 张，
信息密度合理。实测 `COSV5` 2026年04月一个月有 1,801 张，是这个粒度的典型规模。

**id 稳定性在这里更关键**：虚拟套图的 id 用 `vkey = "{分组绝对路径}#{YYYYMM}"` 做键
（不是 `path`）——同一个分组目录下有多个月份，只用 path 会互相覆盖。
新增月份时已有月份 id 不变，缩略图不受影响。

**漫画模块**：`manga: true` 的条目**不进写真网格**（`DB.sets`），走 `DB.mangaSets`，
侧栏有独立入口（有数据才显示，空则不露出）。切换时 `DB.active` 指向对应集合，
`computeFiltered` 只遍历 `DB.active`——复用同一套渲染逻辑，没有复制一份网格代码。
漫画没有标签体系，所以 `html[data-kind="manga"]` 下用 CSS 隐藏人物/标签筛选，
避免出现「点了必然空结果」的筛选项。

**⚠️ manga 标记必须从分组名继承，不能只在散图聚合时判断**（2026-10-26 修的 bug）：
早期只在 `scan_loose()` 里判断 `RE_MANGA_GROUP`，导致 `媚黑NTR漫画库♠️` 下的
**260 个套图全部被当成写真挤进主网格**，漫画模块只剩 10 个散图集。
修法：在 `scan()` 生成套图记录时也写入 `'manga': bool(RE_MANGA_GROUP.search(d0))`。

判断依据只能是**分组名**：`媚黑资源库（四周目）`（1,487 套）名字不含关键词，
实测内容是混合的（真人照片 + 漫画页 + 游戏截图 + 衣柜照），归为写真是对的。

当前规模（2026-10-26 数据）：

| 类型 | 条目 | 图片 |
|---|---|---|
| 写真网格 | 7,518 | 165,214 |
| 漫画（260 套图 + 10 散图集） | 270 | 22,714 |
| **合计** | **7,807** | **188,379**（另 300 张为隐藏的引流目录） |

### 广告式目录名：改名，不删文件

有些目录名长这样：`更多TG搜索@douzi233233_bot`、`入门_裸聊_定制 色色联系 @qqd99`、
`📌 近期精选（点击预览 👀）`。第一反应是"这些是广告，删掉"。

**但抽样逐张看图后结论相反**：`更多TG搜索@douzi233233_bot` 里 226 张**全是 cosplay
真人写真**，一张广告都没有。目录名只是发布者拿来做 TG 推广位，**内容是真的**。

| 目录 | 张数 | 实际内容 |
|---|---|---|
| `更多TG搜索@douzi233233_bot` | 226 | 全是真人写真 |
| `tg搜索douza23333` | 76 | 全是真人写真（春节红装）|
| `📌 近期精选（点击预览👀）` | 9 | 全是真人写真 |
| `入门_裸聊_定制 @qqd99` | 25 | 23 张真人 + 2 张聊天截图 |

所以处理方式是 `clean_ad_names()`：**只洗显示名，一个文件都不动**。

- 剥掉 `@账号`、`TG搜索`、`douzai\d+`、`📌`、`接单/裸聊/定制/入门/线上/滴滴` 等话术
- 洗完之后如果不像正常标题（太短 / 只剩通用词 / 原目录名是一整句广告），
  统一叫 `匿名合集 · N张`，靠张数和封面区分
- 原名保存在 `adname` 字段，可溯源
- 实测清洗 43 个，其中 32 个落到「匿名合集」

**教训**：按目录名判断内容类型会翻车。名字是广告 ≠ 内容是广告。

### 小说模块（独立数据源）

小说在**另一个根目录**（`E://Download//novel_download`），和图片库完全分离：

| | 图片库 | 小说库 |
|---|---|---|
| 根目录 | `E://download//Telegram` | `E://Download//novel_download` |
| 数据 | `index.final.json`（9.7 MB） | `assets/novels.json`（约 500 KB）|
| 展示 | 图片网格 + 虚拟滚动 | 纯文本列表 + 分页 |
| 封面 | 缩略图 + LQIP + 2x | **没有**（用书名 + 分类 + 字数代替）|

**为什么用列表不用网格**：小说之间靠文字区分，网格会浪费横向空间；
而且没有封面，网格只会得到一片空白方块。

**字数用 `size / 3` 估算**（UTF-8 中文约 3 字节一字），不读全文——
4,049 本 2.6 GB 全读一遍要一两分钟，估算误差对"这本书多长"够用。

**懒加载 + 启动预加载**：进小说视图才拉数据，但启动时也要预拉一次——
因为导航项要根据数据决定显隐，而"进视线"又依赖导航项可点，不预加载就是死锁。

规模：**4,049 本 / 2,658 MB / 15 个分类**，分页每次 80 条，支持书名搜索 + 分类筛选。

**下载路由**：`/novel/<相对路径>`（`serve.py`），带路径穿越防护——
解析后的绝对路径必须仍在 `NOVEL_ROOT` 内，否则 404。

### 版本号必须覆盖代码，不只是数据

第一版 `version.json` 只算 `index.final.json` 的哈希。结果：改 `app.js` 之后版本号不变，
手机继续跑旧脚本（索引是新的、逻辑是旧的，比"全都旧"更难排查）。

现在哈希输入 = `index.final.json` + `app.js` + `style.css` + `index.html`
（index.html 要先剥掉自己的 `?v=` 值，否则算哈希会自我循环）。

### 视频怎么处理

全库 **53 个视频 / 2.37 GB**，格式 mp4 + webm（多为 Telegram 动态贴纸和短视频），
分布在 12 个条目里；其中 2 个条目**只有视频没有图片**。

**之前的处理是：直接跳过**（扩展名白名单只含图片）。等于这 2.37 GB 在界面里不存在。

**现在的处理：作为套图单元内嵌播放**，排在图片之前。

三个技术约束决定了这个方案：

| 约束 | 影响 | 应对 |
|---|---|---|
| 本机**没有 ffmpeg** | 无法抽帧做静态封面 | 用 `<video preload="metadata">` 的首帧当封面（加 `#t=0.1` 强制出画） |
| `serve.py` 的 `/raw/` **原先不支持 Range** | 返回 200 + 整个文件，进度条拖不动，几百 MB 的 mp4 会被整个读进内存 | 实现 HTTP 206 分段 + 流式分块写（256 KB/块），实测 `bytes=0-99` → 206、`bytes=1000-` → 206、越界 → 416 |
| 没有播放器组件 | 自造播放器功能不全 | 直接用原生 `<video controls>`：进度条/音量/全屏/画中画都由浏览器提供 |

**为什么不做独立「视频」模块**：视频本身就是套图内容的一部分（`sticker` 套图里
16 个 webm 是同一组贴纸），拆出去反而割裂。漫画模块能独立，是因为漫画是另一种
**内容类型**；视频只是**另一种媒介**。

**卡片标注**：档案章里显示「N 张 · M 视频」，避免用户以为只有图片。

**`.part` 残片**：`cosplay 写真[NSFW]` 下有 11 个 `xxx.jpg.part`（每个 128 KB，
下载中断的半成品）。扩展名是 `.part` 不在白名单里，自动被排除，不会污染图库。

### 为什么不用 OCR 补救

有人会想「剩余未分类的能不能靠 OCR 识别图片文字自动分类」。**实测不可行**，原因在素材本身：

抽 12 个未分类套图的封面逐张看，**12 张里只有 2 张含文字**，且都是噪声——
一张是「TG资源站 / Telegram必备工具」的纯色广告图，一张是抖音账号截图。
写真照片天然没有文字，OCR 只能捞到引流广告。

三条自动化路径的实测覆盖率：

| 路径 | 能补什么 | 实测覆盖率 |
|---|---|---|
| OCR 识别图片文字 | 几乎没有可用信息 | **0%** |
| 读图片文件名 | 无（全是 `20261025_33391.jpg`） | **0%** |
| 视觉识别画面内容 | 主题（内衣/私房/女仆/女巫/蛋糕/卧床…） | ~58%，但粒度粗 |
| 视觉识别画面内容 | **角色 / 作品名** | ~8%，且需目录名提示 |

问题在于：**最有搜索价值的是角色和作品名，而这恰恰是视觉识别最弱的地方**。
视觉能说出「这是女仆装」，但说不出「这是碧蓝航线的柴郡」——
除非画面是辨识度极高的官方 IP 造型。

结论：剩下的未分类套图**人工标注是唯一可靠手段**，界面已提供右键修正标签类型。

### 视觉自动标注（auto-tags.json）

对目录名里确实没有内容信息的套图，用多模态视觉识别补一层**主题标签**。

**产出**：`assets/auto-tags.json`（25 KB）
```json
{ "1234": {"tags": ["内衣","黑丝"], "src": "vision", "at": "2026-10-26T00:40:00"} }
```

## 7.6 手机访问（私有隧道 + 令牌）

### 移动端适配（必须先修的两个缺陷）

用 iPhone 13 视口（390×844, DPR 3）实测，发现两个真缺陷：

**① 侧栏在手机上仍占 248px，主区只剩 142px**

`#app` 的 grid 实测是 `248px 142px`，卡片 220px 直接溢出。根因是 CSS 优先级：

| 位置 | 规则 | 优先级 |
|---|---|---|
| `style.css:1049`（`@media max-width:1279px`） | `.app[data-sidebar="expanded"]` | (0,2,0) |
| `style.css:1071`（`@media max-width:767px`） | `.app` | (0,1,0) |

HTML 上是 `data-sidebar="expanded"`，所以 767px 那条**永远打不过** 1049 行——
侧栏 `transform: translateX(-100%)` 视觉上移走了，grid 却仍然给它分配宽度。
修法：767px 段把选择器补全到同特指度（`.app, .app[data-sidebar="expanded"], .app[data-sidebar="collapsed"]`）。

**② 390px 被判成 1 列**

原断点 `≥1440:6 · 1100:5 · 860:4 · 620:3 · 400:2 · <400:1` 是**按桌面窗口缩放**设计的，
套到手机上，iPhone 全系（390–430px）都落在 1 列，一屏放不下一张卡。
改为 `≥360:2 · <360:1`。**JS 的 `GRID.colSteps` 与 CSS 的媒体查询必须同步改**，否则度量与渲染错位。

修复后实测：卡片 169×313（原 220×381）、2 列、无横向溢出、套图页仍 2 列。

### 访问控制（开隧道前必须做）

`/raw/` 会把 E 盘原图直接吐出去，裸奔到公网等于把 27.3 GB 素材挂在随机域名上。
`serve.py` 加了令牌校验：

| 来源 | 行为 |
|---|---|
| `Host` 为 `127.0.0.1` / `localhost` | 直通（自己用不受影响）|
| 外部 + `?t=<令牌>` | 302 重定向到干净 URL，并种 Cookie（30 天）|
| 外部 + Cookie `gt=<令牌>` | 放行 |
| 外部无令牌/错令牌 | 401 |

令牌来源优先级：`--token=` 参数 > `GALLERY_TOKEN` 环境变量 > 随机生成。
启动时打印并写入项目根目录 `.gallery-token.txt`。

实测 7 个场景全部符合预期，包括 `/raw/` 与 `index.final.json` 都不能绕过。

### 移动端封面清晰度（2x 缩略图）

手机 DPR 3 下 2 列时封面显示 167px，需要 501px 素材，而 1x 只有 240px
→ **有效 DPR 仅 1.44**，肉眼可见发糊。

`build.py` 额外生成 `@2x` 版（480×616，quality 70）：

| 版本 | 数量 | 总体积 | 平均 |
|---|---|---|---|
| 1x（240×308） | 6,367 | 76.9 MB | 12.4 KB |
| 2x（480×616） | 6,367 | 214.2 MB | 34.5 KB |

**加载策略**：用 `devicePixelRatio > 1.5` 判断，而不是 `srcset`——
`srcset` 不配 `sizes` 会按 100vw 估需求，桌面大屏反而会选中 2x，白花流量。

实测分流正确：

| 设备 | 加载版本 | 有效 DPR |
|---|---|---|
| 手机 DPR 3 | 10/10 全部 2x（480px） | **2.87**（原 1.44）|
| 桌面 DPR 1 | 30/30 全部 1x（240px） | 1.25，未白加载 |

### 索引预压缩（手机首次加载）

索引 8.2 MB，手机 4G 首次打开要等好几秒。`build.py` 额外产出 `index.final.json.gz`
（**8.2 MB → 1.14 MB**，压缩 87%），`serve.py` 只在客户端声明 `Accept-Encoding: gzip`
时直接返回 `.gz`（带 `Content-Encoding: gzip` 和 `Vary`），否则回退原文件。
实测本地与公网（Cloudflare 透传）都命中 1,195,255 字节。

### 隧道

`tools/cloudflared.exe`（便携版，不装系统），`手机访问.bat` 一键启动。
临时隧道地址形如 `https://xxx.trycloudflare.com`，**每次重启都会变**。

**长期方案**（需要 Cloudflare 账号 + 自己的域名）：
1. `cloudflared tunnel login` 授权域名
2. `cloudflared tunnel create gallery` 创建命名隧道
3. 配 DNS CNAME 指向 `<tunnel-id>.cfargotunnel.com`
4. 用 `cloudflared service install` 注册成 Windows 服务（开机自启，不用手动开窗口）

### 合规风险（重要）

Cloudflare Pages / R2 / GitHub Pages 的 ToS 都禁止成人内容。**私有隧道不走静态托管**，
只有持令牌者能访问，风险远低于公开站点。但把素材做成公开可访问的站点，仍有封号风险。

## 7.7 小说库：目录形态、版本号与自动重建

小说和图片是两套完全独立的数据，只共用同一个页面外壳。小说库 4000+ 本 / 2.6 GB 纯文本，
扫描耗时 0.1 秒（字数是 `size/3` 估算，不读全文），所以可以随时重建。

### 三种目录形态（外加一个曾经踩到的坑）

```
A   <分类>/<书名>.txt                 历史数据的平铺结构
B1  <分类>/<书名>/<书名>.txt          爬虫主流输出（配 meta.json）
B2  <分类>/<书名>/chapters/*.txt      分章存储，walk 时按文件名排序拼接
B3  <分类>/<聚合层>/<书名>/...        爬虫多套了一层
```

**B3 是个隐蔽 bug**：cool18 爬虫把书存到 `novel_download/cool18/cool18/<书名>/`，
比预期多一层。原来的 `scan_novels()` 只扫两层，于是把整个 `cool18/cool18` 当成**一本书**，
几十本书合并成一条叫「cool18」的巨大条目——列表里看着像"抓了但没生效"。

判定规则（`scan_novels()` 里）：
1. 目录第一层有 txt → 是书（B1）
2. 否则看直接子目录里含 txt 且**名字不像章节容器**的（排除 `chapters`/`正文`/`content`）
3. 这样的子目录 ≥ 2 个 → 是聚合层，逐个展开成书（B3）
4. 否则 → 整目录当一本书（B2）

阈值取 2 是因为 `chapters` 只有一个；再低会把 B2 拆散。

### 版本号必须拆成两个（v 和 nv）

`assets/version.json` 现在长这样：

```json
{"v": "bd53b0006681", "nv": "af353a27f31b", "at": 1792992619}
```

- **v** = 图片索引 + 前端代码（app.js / style.css / index.html 剥掉 `?v=` 后）
- **nv** = 只算 `assets/novels.json`

为什么不能合成一个：索引 gzip 后还有 **1.34 MB**，而小说库在爬虫跑的时候每几分钟就变一次。
共用一个版本号的话，手机每次刷新都要白下 1.34 MB 完全没变的图片索引。
拆开后小说更新只影响 0.67 MB 的 `novels.json`。

前端对应 `DB.version` / `DB.nversion`，`loadNovels()` 用后者。

### 抓完自动重建：serve.py 里的看门狗

爬虫要跑几小时，抓完不该靠用户记得手动重建。`serve.py` 起一个 daemon 线程
（`novel_watchdog`），每 60 秒算一次小说目录的指纹：

- **只看到第二层**：分类目录的 `mtime` + 直接子项数；聚合层（`cool18/cool18`）再单独看一层。
  书内 txt 追加（追更）不影响列表，不用管。实测 8 ms，可以每分钟跑。
- 指纹变了、且距上次重建 ≥ 5 分钟 → 起 `build.py --novels`（0.1 秒）
- `--novels` 只重建小说库 + 版本号，**跳过 14 万张图的扫描**，不碰缩略图

**踩过的坑：不要写「等目录安静 N 分钟再重建」**。抓取是连续写的，每抓完一本目录就变一次，
"安静 3 分钟"在整个抓取期间根本不会出现——那样写的话一次都不会触发。
重建只要 0.1 秒且是原子替换（写 `.tmp` 再 `os.replace`），抓到一半重建完全安全，
直接用时间节流就够了。

需要单独跑（服务已经在跑、不想重启时）：`python app/novel_watcher.py`，
它复用 serve.py 里的同一份逻辑，不重复实现。
