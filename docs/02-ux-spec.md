## 1. 信息架构（IA）

### 1.1 层次判定：3 层还是 4 层？

先说结论：**采用 3 层导航 + 2 个正交维度**，不采用「标签聚合页 → 套图 → 照片 → 灯箱」的 4 层嵌套。

理由（基于实测）：

1. **标签不是层级，是维度。** 若把「标签聚合页」放在套图之上，会形成 `标签页 → 套图页 → 照片流 → 灯箱` 的 4 层链路，用户从「按角色找」到「看图」要点 4 次。且 42.7% 的套图没有可识别的作品/角色/主题标签，把它们藏在标签体系下等于**让近半数据不可达**。
2. **但标签聚合是真实高频需求**（「按标签找某个角色的全部写真」是任务简报明确列出的主线）。解决方案是把它做成**顶层 Tab**（与套图集平级），而不是父级页面。
3. **套图集（gallery）是内容单元，不是容器层级。** 一个套图目录 = 一个不可分割的内容包（6–130 张，共享同一组标签），必须整体呈现为卡片，用户点进去才展开。

### 1.2 IA 决策表

| 候选结构 | 结论 | 理由 |
|---|---|---|
| **顶层 = 套图集（画廊网格）** | ✅ 采用 | 5292 个套图是内容主体；卡片网格可扫视、可比较封面 |
| **中层 = 单套图的照片流** | ✅ 采用 | 套图内部共享元数据，一次进入、连续浏览 |
| **顶层 = 标签聚合页** | ✅ 采用（平级 Tab） | 满足「按角色找」；不强制经过它 |
| 顶层 = 套图集 / 中层 = 标签页 / 底层 = 套图 | ❌ 拒绝 | 4 层点击；且套图页被包在标签下会让无标签套图失联 |
| 顶层 = 文件系统树（2 层分组 → 套图） | ❌ 拒绝 | 顶层 2 个目录名是运营文案（`COSV5_COSER_写真_JVID_及时发布全网流出🚀`），不是有意义的分类，对用户零价值 |
| 按 coser 分层（coser → 套图 → 照片） | ❌ 拒绝 | 同上，coser 聚合是**横切视图**，不是树 |

### 1.4 层级数与路由映射

| 层级 | 名称 | 路由 | 数量级 |
|---|---|---|---|
| L0 | 全局外壳 | — | 1 |
| L1 | 全部套图 / 按标签浏览 / 最近新增 | `/` `/tags` `/recent` | 3 |
| L2 | 单套图 | `/set/:id` | 5292 |
| L3 | 灯箱 | `/set/:id?i=12`（URL 同步，不新开历史记录） | 85393 |

**路由决策**：灯箱用 query 参数 `?i=12` 而非独立路由。原因：灯箱是 L2 的模态叠层，独立路由会让浏览器后退键行为混乱（后退到底是"退灯箱"还是"退套图页"）。用 query 时：后退 = 关灯箱（符合直觉），再后退 = 回套图列表。

### 1.5 「按标签浏览」页的交互定位（关键取舍）

标签页**不新建结果页**。点标签 → 跳到 `/` 并把该标签作为已应用筛选，chips 区可见、可移除。

理由：
- 避免同一批结果有两个渲染路径（标签页结果 vs 全部套图页结果），减少一处状态同步 bug。
- 让用户始终知道"我现在在一个被筛选的视图里"，而不是"我在另一个页面"。
- 代价：从标签页跳走时丢失标签页的滚动位置 → **必须实现**：跳转前把 `tags` 维度 + 滚动位置存入 sessionStorage，返回时恢复。

## 2. 核心任务流（4 条主线）

每条流程标注**界面状态**（对应 §4 的状态机命名）。

### 流程 A：按标签找某个角色的全部写真

> 目标：从"我想看 XXX 这个角色的写真"到"看到全部相关图"。

| 步 | 用户动作 | 界面状态 | 系统行为 | 耗时目标 |
|---|---|---|---|---|
| A1 | 打开应用 | `L1-A · grid-loading` | 读 `library-index.json`，渲染首屏 24 张卡片 | 首屏可交互 ≤ **800 ms** |
| A2 | 点侧栏「按标签浏览」 | `L1-B · tags-loading` → `L1-B · tags-ready` | 标签云按频次倒序；角色维度默认选中 | ≤ 200 ms |
| A3 | 搜索框输入角色名（如「爱弥斯」） | `L1-B · tags-filtering` | 前缀匹配 + 拼音/罗马音匹配，命中 ≥2 时给下拉建议 | ≤ 80 ms |
| A4 | 点「爱弥斯」（5 套图） | `L1-A · grid-ready` + 筛选 chips=[爱弥斯] | 跳转到 `/`，套图卡片网格只显示 5 张，chips 可见 | ≤ 150 ms |
| A5 | 点第 1 张卡片 | `L2 · stream-loading` | 进入套图页，照片流加载 5 张缩略图 | ≤ 300 ms |
| A6 | 滚动/翻页浏览 | `L2 · stream-ready` | 无限滚动追加，滚动进度条显示 "3 / 5" | 每张追加 ≤ 60 ms |
| A7 | 点任意图 → 灯箱 | `L3 · lb-loading` → `lb-loaded` | 原图加载，显示元数据面板 | 原图 ≤ 600 ms（本地 SSD） |

**关键决策**：
- A4 的 chips 必须**可见且可点**。用户搜了角色就跳走、没有筛选痕迹，会导致"我怎么只看到 5 张"的困惑。
- A3 的角色名有罗马音/中文混写问题（`爱弥斯` / `Aimes` / `エimest`），搜索框必须做 **NFKC 归一化 + 大小写不敏感 + 去符号**，这是 `key()` 函数的同一套规则。

### 流程 B：浏览某个 coser 的全部套图

| 步 | 用户动作 | 界面状态 | 系统行为 |
|---|---|---|---|
| B1 | 点侧栏 coser 搜索框，输入「纸悦」 | `L1-A · sidebar-search` | 模糊匹配 → 建议列表（头像占位 + 套图数） |
| B2 | 选中「纸悦Etsu_ko（43 套图）」 | `L1-A · grid-ready` + chips=[coser:纸悦Etsu_ko] | 网格过滤，**保留当前排序**（默认按最近新增） |
| B3 | 卡片显示 | — | 卡片副标题固定显示 `coser · 标签1 · 标签2`，让用户不点进去也能区分 |
| B4 | 某套图内查看「该 coser 的其他套图」 | `L2 · panel-open` | 元数据面板底部列出同 coser 的其他套图（横向缩略条），点击直接切换 |

**关键决策**：
- B4 的"同 coser 其他套图"是本任务流的收口。实测 top coser 有 91 套（`年年`）、76 套（`Bangni邦尼`）、58 套（`麻薯好吃`）——如果没有这条出口，用户找完一套图后**没有任何路径**到下一套，只能回退到侧栏重选。这是本 IA 最容易漏掉的一条。
- coser 名在 1886 个唯一值中存在大量同一人的不同写法（`#洛璃LoLiSAMA` / `#洛璃(` / `#LoLiSAMA`）。**必须做别名合并**，否则"按 coser 浏览"会出现 3 个只差一个字的条目。

### 流程 C：在一套图里翻页 / 快速比对

| 步 | 用户动作 | 界面状态 | 系统行为 |
|---|---|---|---|
| C1 | 在 L2 套图页 | `L2 · stream-ready` | 网格视图（默认），显示 5 列缩略图 |
| C2 | 点「照片流」切换 | `L2 · filmstrip-mode` | 切换为单列大图流（宽 720–960 px），支持一次显示 1 张 |
| C3 | 在大图流按 `→` / `←` | `L2 · filmstrip-nav` | 切到下一张，预加载 ±2 张 |
| C4 | 点「对比」按钮 | `L2 · compare-mode` | 进入对比模式：最多选 4 张，2×2 网格并排，缩放同步 |
| C5 | 对比模式下 `Esc` | `L2 · stream-ready` | 退出对比，选中态清空 |

**关键决策**：
- C2 的「照片流」不是灯箱的替代品。灯箱是**看单张大图 + 元数据**，照片流是**连续翻阅不打断**。两者的滚动模型不同（灯箱是翻页式，照片流是连续式）。
- C4 对比模式是本场景的独特需求：写真套图的购买/筛选决策常常基于"哪张更好"。2×2 同步缩放对比，比在一堆缩略图里来回点高效得多。**限制 4 张**（2×2），超过 4 张时给出提示"最多对比 4 张"，而不是无限扩张导致布局失控。

### 流程 D：只看最近新增

| 步 | 用户动作 | 界面状态 | 系统行为 |
|---|---|---|---|
| D1 | 点侧栏「最近新增」 | `L1-C · timeline-loading` | 读索引里的 `shotDate` 字段（套图内文件名众数日期） |
| D2 | 看到时间线 | `L1-C · timeline-ready` | 按日期分组：今天 / 昨天 / 本周 / 更早。**按日期分组而非纯列表** |
| D3 | 想看"这一批" | — | 每组头部显示"共 N 套"，可折叠 |
| D4 | 点卡片 | `L2 · stream-loading` | 进入套图 |

**关键决策（重要）**：
- **绝不能用目录 mtime**（实测全部落在 3 天内，见 §0）。必须用**套图内文件名的 `YYYYMMDD` 众数**。
- 实测 400 个抽样套图中，26 个（6.5%）内部含**多个不同日期前缀**（跨天拍摄）。众数法取最多日期；同时在套图页显示「跨越 3 个拍摄日」的次要信息。
- 时间线默认窗口是「最近 7 天」，而不是一次性列出全部。因为 85393 张图按日期铺开是 300+ 天，**没有分页的无限时间线会是无底的**。提供「加载更早」按钮（每次 30 天）。

## 3. 从目录名解析元数据（可执行规则）

这是本项目最硬核的工程点。**目录名是唯一元数据来源**（无数据库），解析质量直接决定整个应用是否可用。

### 3.1 总体管线（两级架构）

采用**两级解析**，因为单遍解析无法区分"角色"与"主题"——这需要全库共现信息。

```
Pass 1（一次性，113 ms / 全库）
  扫描 5292 个目录名 → 构建：
    COSER_TABLE   1886 个 coser 名（归一化后，含联合 coser）
    ALIAS_TABLE    101 个别名（括号内罗马音、括号内真名）
    TAG_FREQ       3360 个标签的频次
    TAG_PARTNERS   标签共现伙伴集合
    TAG_CONC       标签与单一伙伴的最大共现占比（集中度）

Pass 2（逐目录，0.051 ms/目录，267 ms 全库）
  S0 规范化 → S1 剥规格 → S2 抽括号组 → S3 深度切分 → S4 取 coser
  → S5 标签分块 → S6 裸词拆分 → S7 三层证据分类 → S8 时间提取
```

### 3.2 S0 规范化（normalize）

```python
def norm_text(s):
    s = unicodedata.normalize('NFKC', s)          # 全角→半角、①→1
    s = s.replace('&amp;','&').replace('&gt;','>')
    s = s.replace('&lt;','<').replace('&quot;','"')
    s = re.sub(r'[\u200b-\u200f\ufeff]', '', s)    # 零宽字符
    for d in '‐‑‒–—―−－ー~～': s = s.replace(d, '-')   # 7 种破折号/波浪号→'-'
    return re.sub(r'[ \t]+', ' ', s).strip()
```

**为什么需要 NFKC**：实测存在全角括号 `（`，而部分目录用半角 `(`。不归一则括号配对失败 → 整段解析崩。

**为什么需要破折号归一**：实测使用 `–`（en dash）、`—`（em dash）、`ー`（片假名长音）、`~`。不归一则分隔符检测漏检 → head/tail 切错。

**标签归一化键（key）**，用于比较、去重、搜索：

```python
def key(s):
    s = norm_text(s).lower()
    return re.sub(r'[\s\-_·・.,、\'"!?,，。！?]+', '', s)   # 去所有分隔符
```
例：`NIKKE` / `nikke` / `Nikke ` → 全部折叠为 `nikke`；`兔女郎` / `兔 女郎` → `兔女郎`。

### 3.3 S1 剥离规格标记

实测规格形态有 4 类，必须分别处理：

| 形态 | 实例 | 正则 | 提取为 |
|---|---|---|---|
| 方括号规格 | `[39P-390MB]` `[120P-1.02GB]` `[57P-17MB]` | `RE_SPEC_BRACKET = re.compile(r'\[[^\[\]]*\]')` | 丢弃（仅用于体积提示） |
| 裸「页数-体积」 | `96P1V1.49GB` `316MB` | `RE_SPEC_PAIR = r'(\d+\s*[Pp]\s*\d*\s*[Vv]?)\s*[-–]?\s*(\d+(?:\.\d+)?\s*[MmGg][Bb]?)'` | `pages`, `size` |
| 裸页数 | `25P` `49p` | `RE_COUNT = r'(?<![\w.])\d{1,4}\s*[Pp](?:\s*\d{1,2}\s*[Vv])?(?!\w)'` | `pages` |
| 裸体积 | `472MB` `1.34G` | `RE_SIZE = r'(?<![\w.])\d+(?:\.\d+)?\s*[MmGg][Bb]?(?!\w)'` | `size` |

> ⚠️ **顺序陷阱 1**：必须**先匹配 PAIR 再匹配 COUNT**。否则 `96P1V1.49GB` 会先被 COUNT 吃掉 `96P1V`，剩下 `1.49GB` 被当体积——虽然结果碰巧对，但 `40P1V-1.15GB` 这类会漏掉 `1V`（视频数）。**页数/视频数/体积三个维度都要保留**，因为 `[120P-1.02GB]` 里的 `120P` 是用户的核心预期信息（套图张数），UI 上必须显示。

> ⚠️ **顺序陷阱 2（实测发现并修正的 bug）**：**方括号内的规格必须先提取、再剥离整块**。若直接 `RE_SPEC_BRACKET.sub(' ', name)` 先删掉 `[51P7V-235MB]`，则 `pages`/`size` 字段全为空（实测提取率为 0）。正确顺序：先对每个方括号块的内容跑 PAIR/COUNT/SIZE 提取，**再**把整个方括号块从串里删除。
> 修正后实测：**页数提取率 79.8%，体积提取率 74.2%**。剩余 20% 的套图目录名确实不含规格信息（例：`#二佐Nisa`、`#纸悦Etsu_ko - #鸣潮 #爱弥斯`），这部分靠 §8.2 的 P1 后台补齐真实张数。

### 3.4 S2 括号组提取（split_groups）

括号内内容**不是标签正文**，但括号内的 `#token` 是标签。必须做**深度配对**扫描，而不是正则替换。

```python
BRACKETS = {'(':')','（':'）','[':']','【':'】','「':'」','『':'』','《':'》','{':'}'}
# 扫描栈式配对，返回 (去括号后的串, 各组内容)
```

规则：
- 括号组内含 `#token` → 该 token 进入标签池（例：`#Machi (#馬吉 - #大黑塔 ...)` 中 `馬吉` 是别名，`大黑塔`/`水着` 是标签）。
- 括号组内**不含** `#` 的纯文本 → 丢弃（例：`（点击预览 👀）`、`（ #amasone )` 的说明部分）。
- 括号内容**不参与 coser 拼接**。

### 3.5 S3 深度 0 分隔符切分

```python
def depth_split(s):
    # 在括号深度为 0 的位置找第一个 " - "（前后各需一个空格）
```

**必须是深度 0**：实测存在 `#Machi (#馬吉 - #大黑塔 #水着💜 ...)`，其中的 ` - ` 在括号内。若不处理括号深度，整串会被切成 `head='#Machi (#馬吉'` / `tail='#大黑塔 ...'`，导致 `馬吉` 被误判为独立标签、`Machi` 丢失同括号名的关联。

**分隔符必须是 `" - "`（带空格）**，不能是裸 `-`：实测存在 `#九柒喵 - #无职转生`、`#CosV5 #日式 cos - #泳装`，但也存在 `#Umeko J – Mai Shiranui Casual - Dead or Alive`（英文标题含 `-`）和 `#PoppaChan - Frieren Blue Valley Dress`。带空格 + 深度 0 双重约束后，`Dead or Alive` 前的 `-` 仍会被误切 —— 所以 **S4 必须能处理"tail 缺失"的情况**（此时整串都是 coser 名，标题归入 `others`）。

### 3.6 S4 取 coser 段

```
head 段结构化拆解：
  head = "#coser1 [&/#coser2 ...] [#tag ...]"
  ├─ 第 1 个 #块  → 主 coser
  ├─ 第 2+ 个 #块  → 若在 COSER_TABLE 中 → 联合 coser（co-coser）
  │                 若与主 coser 归一化后互为子串 → 别名
  │                 否则 → 进标签池（head 标签）
  └─ 裸词（无 #） → 主 coser 的组成部分
```

**实测的 5 种 coser 形态**（规范必须全部支持）：

| 形态 | 实例 | 处理 |
|---|---|---|
| 单名 | `#纸悦Etsu_ko` | 直接取 |
| 中英混写 | `#yoshioka 桃井` `#YoKei 约柯` | 整段保留为 coser 显示名 |
| 括号别名 | `#Machi (#馬吉)` `#Hanari( #하나리)` | 主名 + 别名（进 ALIAS 判定） |
| 联合 coser | `#水淼 & #清水由乃` `#九曲Jean #二佐Nisa` | `&` 分隔 → co-coser 数组 |
| 频道名混入 | `#CosV5 #日式 cos` | 第 1 块 `CosV5` 是 coser，`日式 cos` 是标签 |

> ⚠️ **`#CosV5 #日式 cos - #泳装` 是最难的样本**：head 有两个 `#` 块，第一个是频道/作者名，第二个是标签。若按"第 2 块 = co-coser"处理，会把 `日式 cos` 塞进 coser 字段。判据：**若第 2 块在 COSER_TABLE 中 → co-coser，否则 → 标签**。实测 `日式 cos` 不在 coser 表中 → 正确进标签池。

> ⚠️ **别名判定不能靠字符重叠**：`#Hanari( #하나리)` 的别名是韩文，与 `Hanari` **无一字符相同**；`#Machi (#馬吉)` 同理。正确判据是**全库共现**：统计「主 coser + 括号内 token」的共现对数，**≥ 2 个目录**即认定别名。实测 Pass1 收集到 **287 个共现对**，运行时据此判定，**183 个套图**被正确识别出括号内真名（例：`#CatDemon( #你的喵崽` → 别名 `你的喵崽`）。

> ⚠️ **未闭合括号必须处理**：实测存在 `#Machi (#馬吉 - #大黑塔 ...` 这种**缺少右括号**的目录名（实测 101 个括号 token 中有相当比例）。若括号内容泄漏回主串，其中的 ` - ` 会变成假分隔符，导致整个 head/tail 切分崩溃、所有标签丢失。**规则：未闭合括号的内容不得回填主串**，且原括号深度 > 0 的 ` - ` 必须还原为普通空格。

### 3.7 S5–S6 标签分块与裸词拆分

**分块**：按 `#` 切分，每块 = 一个候选标签。

**裸词拆分**（关键）：一个块内可能有多个词，其中一部分是已知词（作品/角色/主题/coser），其余是描述性长词。规则：

```
若块内某词在 WORKS ∪ ROLES ∪ THEMES ∪ PSEUDO ∪ COSER_TABLE 中：
    → 该词独立成项
否则：
    → 累积到 buffer，与相邻未知词合并
```

实例：
- `#日式 cos` → `日式` 未知 → buffer=`日式`；`cos` 未知 → buffer=`日式 cos` → 合并为 1 项 ✅
- `#Swimsuit The Herta` → 全部未知 → 合并为 1 项 ✅
- `#精油 #SPA` → 拆成 2 个独立块 ✅

**时间/计划词剥离**（S6 内）：裸词块若完全匹配时间正则 → 归 `times`，不进标签池。

```python
RE_TIME = re.compile(
    r'(\d{2,4}\s*年\s*\d{1,2}\s*月(?:\s*计划\s*[A-Za-z0-9])?|'
    r'\d{4}\s*[.\-/]\s*\d{1,2}(?:\s*[.\-/]\s*\d{1,2})?|'
    r'\d{1,2}\.\d{1,2}\s*月号|\d{1,2}\s*月号|'
    r'\d{4}\s*年(?:\s*\S{1,4}年?)?|'
    r'计划\s*[A-Za-z0-9]|Tier|Part\s*\d+|第\s*\d+\s*[期回]|'
    r'(?<![\d\w])\d{1,2}\s*[-–]\s*\d{1,2}(?![\d\w])|'
    r'\d{4}[A-Za-z]{3}(?:\d{2})?)')
```

实测覆盖：`25年12月计划A`、`26-8`、`23.9月号`、`2025.Jan-Tier`、`26年04月`、`4月惊喜掉落`（部分）。

**emoji 剥离**：任何标签中的 emoji 序列 → 剥离后若剩余为空 → 整项丢弃（`#💜`、`#🐭🧀`）；若剩余有文字 → 保留文字，emoji 存入独立字段 `emoji`（`#圣诞🎄` → 标签 `圣诞`，emoji `🎄`）。

emoji 正则（覆盖 Unicode 15 主要区块 + VS16 + keycap）：
```python
EMOJI_RE = re.compile(
    '[\U0001F000-\U0001FAFF\U0001F1E6-\U0001F1FF\U0001F900-\U0001F9FF'
    '\u2190-\u21FF\u2300-\u27BF\u2B00-\u2BFF\uFE0F\u20E3\u2764\u2B50]+')
```

> **emoji 的产品决策**：emoji **不作为可筛选标签**。理由：emoji 语义不可靠（`💜` 出现在 16 个套图、`♨️` 表示温泉主题、`🎂` 表示生日），且 emoji 无法被搜索到。emoji 只保留为**装饰性标记**显示在标签旁。**唯一例外**：emoji 与文字组合时（`#圣诞🎄`）保留文字部分 `圣诞` 作为可搜标签。

### 3.8 S7 三层证据分类（作品 / 角色 / 主题 / 未分类）

**这是全项目最难的问题**。实测证明单纯统计不可靠：

| 判据 | 实测结果 | 结论 |
|---|---|---|
| 共现伙伴数 ≥ 8 → 作品 | `兔女郎` 142、`女仆` 94、`泳装` 68 全被误判为作品 | ❌ 不可用 |
| 共现伙伴数 ≤ 4 → 角色 | `私房` 14、`旗袍` 70 被误判 | ❌ 不可用 |
| 共现集中度 ≥ 0.28 → 角色 | `私房` 0.30、`旗袍` 0.17、`水着` 0.23 混乱 | ❌ 单独不可用 |

**根本原因**：本库中「角色」与「主题」的边界本身就是模糊的。`兔女郎`（82 次）既是服装主题也是人设标签；`拉菲兔`（7 次）是角色；`水着`（7 次）是服装。**靠共现统计无法区分**。

**因此采用三层证据加权打分**（每层独立、可单独调参）：

```
score['work'], score['role'], score['theme']

证据 A — 硬词库（命中即 +0.60）
  A1 ∈ WORKS  → work += 0.60
  A2 ∈ ROLES  → role += 0.60
  A3 ∈ THEMES → theme += 0.60

证据 B — 位置模式（+0.15 ~ +0.30）
  若同目录首标签是已确认作品：
      i==0 → work += 0.25
      i==1 → role += 0.30
      i>=2 → theme += 0.30
  否则（无作品锚点）：
      i==0 → work += 0.15 且 theme += 0.15
      i>=2 → theme += 0.20

证据 C — 全库统计（仅在 A/B 都不足以定夺时起辅助作用，+0.15 ~ +0.20）
  freq(t) >= 3 时：
      partners >= 25 且 freq >= 20        → work  += 0.15
      partners <= 12 且 freq <= 60        → role  += 0.15
      集中度 conc(t) >= 0.28              → role  += 0.20
      partners >= 40 且 conc(t) < 0.15    → theme += 0.20
```

**置信度与分档**：

```
top = max(score), second = 次高分
if   top >= 0.60                → conf = 0.99   （词库硬命中）
elif top >= 0.30                → conf = 0.90 if top-second >= 0.25 else 0.65
elif top > 0                    → conf = 0.55 if top-second >= 0.15 else 0.35
if   top < 0.30                 → 归入 others（未分类），conf 照记
```

**兜底设计（关键产品决策）**：
- `others`（未分类）**必须作为一等公民**出现在筛选侧栏的「未分类」分组里，且**默认不折叠**——因为实测 42.7% 的套图只含 others 标签，折叠它等于让近半数据消失。
- UI 上 `others` 桶用虚线边框/次级色与正式标签区分。
- **置信度 < 0.65 的标签在卡片上不显示类型图标**，只显示标签文本；置信度 ≥ 0.65 才加作品/角色/主题的分类标记。这样避免"错误分类"误导用户。

**已知残留误差**（实测诚实披露）：
- `2B`（7）、`尼禄`（7）、`灰姑娘`（10）、`蕾姆`（7）等**长尾角色名**无法靠共现判定（freq ≤ 10），落入 others。
- `Fate`（14）、`永劫无间`（8）、`Bunny`（8）、`同人`（7）等**作品/题材名**同样落入 others。
- **这必须由人工修正解决，不能靠算法**。因此规范要求：UI 提供**标签类型的就地修正**（见 §5.4），修正结果持久化到 `library-overrides.json`，下次启动合并进词表。**这是本场景数据质量的唯一可持续解法。**

### 3.9 S8 时间提取与「拍摄日期」

从目录名提取的 `times`（如 `25年12月计划A`）是**发布/计划时间**，不是拍摄时间。

**拍摄时间**来自文件名：`YYYYMMDD_<id>_<id>.jpg`（实测 100% 覆盖）。

```
套图拍摄日期 = 套图内所有文件名 YYYYMMDD 前缀的【众数】
```
- 26% 的套图（抽样 400 个中 26 个 = 6.5%）含多日期 → 众数法取最多日期，同时记录 `dateSpan`。
- 众数并列时取**最早**日期（保守，更接近"这套图是什么时候开始的"）。
- 无任何合法日期前缀的套图 → 拍摄日期为 null，在「最近新增」中不出现，在套图页显示"日期未知"。

- 规格标记残留 = 0（任何 `[]` 内容不得出现在任何显示字段）
- emoji 残留 = 0（任何标签字段不得含 emoji 码位）
- 索引 JSON ≤ 1.5 MB

### 3.12 与团队既有实现的口径对齐（重要）

前端数据源为 `app/index.final.json`（5292 条，字段：`raw coser co tags works roles themes others series pages size times emoji promo group n count path files kinds id dates date thumb`）。

**「无标签套图」有三个不同口径，数值差异巨大，设计时必须明确用哪一个：**

|---|---|---|---|
| **A. 无任何标签** | `works/roles/themes/others` 四字段全空 | **1435 条（27.1%）** | 卡片**完全无副标题**可用 |
| **B. 无有效内容标签** | `works/roles/themes` 全空（仅 others 或全空）| **3795 条（71.7%）** | 筛选面板「未分类」桶的规模 |

> ✅ **Phase 3 收尾已统一**：全部口径按 `index.final.json` 实际字段 groupby，上表为最终值。早期各版本文档中出现过的「48.0%」「30.0%」「44.9%」等数字均已作废。

### 3.13 作品 / 角色 / 主题的判定策略：与团队实现的差异与改进建议

团队既有实现（`app/parse_lib.py`）采用**两遍数据驱动扫描**：
- 作品词表：`n >= 8 且 c >= 5`（频次 ≥ 8 且覆盖 ≥ 5 个不同 coser）→ 实测 59 个词
- 角色词表：在同套图内与作品标签共现、频次 2~60、长度像角色名 → 实测 256 个

**我实测验证了这条路径的主要风险，并已同步写入我的实现（`parse_rules_proto.py`）**：

> ⚠️ **「频次高 + 跨 coser 复用」不足以判定作品，必须有一层泛化主题词排除。**
> 实测反例（这些词频次高且跨 coser，但都是主题）：`兔女郎(82)` `女仆(46)` `旗袍(48)` `JK(40)` `泳装(36)` `花嫁(20)` `修女(21)` `古装(18)` `黑丝(15)` `私房(10)`。
> 团队实现用约 45 个词的 `GENERIC` 泛化主题表把它们从作品表剔除——**这个做法是对的，必须保留**。
> 但硬编码泛化表有维护成本：新增主题词会漏判。

**我采用的改进策略（三层证据加权打分，见 §3.8）**，与团队实现的关系：

| 维度 | 团队实现（parse_lib.py） | 我的实现（parse_rules_proto.py） | 建议 |
|---|---|---|---|
| 作品判定 | `n>=8 且 c>=5` + GENERIC 表排除 | 硬词库 +0.60 / 位置模式 +0.25 / 统计 +0.15 | **保留我的分层**，但把团队实测出的 59 个作品词与 45 个泛化词作为**种子**注入 `SEED_WORKS` / `SEED_THEMES` |
| 角色判定 | 与作品共现 + 频次 2~60 + 长度 | 硬词库 +0.60 / 位置模式 +0.30 / 统计 +0.15 | 同上，种子注入 |
| 主题判定 | GENERIC 表显式枚举 | `SEED_THEMES` 45+ 词 + 位置模式 +0.30 | 同上 |
| 泛化主题排除 | ✅ 已做 | ✅ 已做（`SEED_THEMES`） | **两边都保留，形成双保险** |
| 置信度 | ❌ 无 | ✅ 有（0.35/0.65/0.90/0.99 四档） | **建议采纳**，UI 靠它决定是否显示类型图标 |
| 长尾兜底 | ❌ 无 | ✅ 人工修正入口 + `library-overrides.json` | **建议采纳**，这是唯一可持续解 |

**这些词在我的策略下应归到哪一类（实测）**：

| 词 | 团队实现 | 我的实现 | 一致？ | 备注 |
|---|---|---|---|---|
| `兔女郎` | 主题（GENERIC 排除）| 主题 | ✅ | 82 次，跨 coser 但语义是服装/题材 |
| `旗袍` / `JK` / `泳装` / `花嫁` / `修女` / `古装` | 主题 | 主题 | ✅ | 同上 |
| `女仆` | 主题 | 主题 | ✅ | 46 次 |
| `碧蓝航线` / `原神` / `鸣潮` / `明日方舟` / `绝区零` / `NIKKE` | 作品 | 作品 | ✅ | 硬词库 + 统计双命中 |
| `爱弥斯` / `霍尔海雅` / `柴郡` / `守岸人` | 角色 | 角色 | ✅ | 位置模式（作品后紧跟）+ 共现绑定 |
| `Eva` / `天命` / `精油` / `SPA` | 角色/作品（有歧义）| **未分类** | ⚠️ 我的更保守 | 长尾（freq 1~2）确实无法判定，交给人工修正 |

**结论与建议动作**：
1. **两边分类结果在高频词上完全一致**（碧蓝航线/原神/鸣潮等作品、兔女郎/女仆/旗袍等主题均判对），互为验证。
2. **差异集中在长尾**（freq ≤ 10）。我的实现**故意不猜**，落入未分类桶 —— 因为错误分类会永久损害用户信任（反模式 §9-6），而"未分类"是诚实的。
3. **具体建议动作**：把团队实测的 **59 个作品词 + 45 个泛化主题词**注入我的 `SEED_WORKS` / `SEED_THEMES`，可让长尾准确率明显提升。这是**纯增量、不改架构**的改动。
4. 若需进一步提高，唯一可持续路径仍是**人工修正回流**（`library-overrides.json`），我的实现已预留该接口。

### 4.2 状态详表

| 状态 | 界面呈现 | 可用操作 | 退出/恢复路径 |
|---|---|---|---|
| `lb-closed` | 不渲染任何 DOM（或保留在 DOM 但 `display:none` + `inert`）| — | 由「打开灯箱」转移进入 |
| `lb-loading` | 主图区：纯色骨架块（尺寸=已知宽高比，避免 CLS）+ 居中进度环；右下角文字「载入中 3/12」；缩略图条已可见并高亮当前项 | `Esc` 关闭 / `←` `→` 直接跳转到相邻（不阻塞）| 原图 decode 完成 → `lb-loaded`；失败 → `lb-error`；`Esc` → `lb-closed` |
| `lb-loaded` | 主图完整显示；底部工具栏；元数据面板按用户上次的展开状态显示 | 见 §4.3 快捷键表 | → `lb-navigating` / `lb-immersive` / `lb-fav-on` / `lb-fav-off` / `lb-closed` |
| `lb-navigating` | 主图保持**上一张**（不闪白）；主图区右下出现细进度条（2 px，高 60% 宽）；新图加载完成后主图**交叉淡入 120 ms** | 可继续按 `→` 快速连翻（队列化，最多预载 3 张）| 新图就绪 → `lb-loaded`；超时 5 s → `lb-error`（保留上一张 + 提示）|
| `lb-error` | 主图区：⚠ 图标 + 「这张加载失败」+ 两个按钮：`重试` / `跳过`；**保留上一张缩略图**，不整屏变黑 | `重试` / `→` `→` / `Esc` | `重试` → `lb-loading`；`跳过` → 下一张 → `lb-navigating`；`Esc` → `lb-closed` |
| `lb-immersive` | 隐藏所有浮层（工具栏/面板/缩略图条）；鼠标移动 3 s 内无操作则保持隐藏，**移动鼠标立即恢复**（不需重新点击）| 移动鼠标 / `Esc` / `→` `←` | 鼠标移动 → `lb-loaded`（恢复上次面板状态）|
| `lb-fav-on` / `lb-fav-off` | 心形图标填充/描边切换；**变化有 200 ms 缩放动画 + 一次颜色闪烁**；无需弹 toast | 继续点按切换 | 即时切回 `lb-loaded` |
| `lb-panel-open` | 右侧元数据面板展开（桌面 ≥ 768 px：宽 320 px 占据右侧；移动端：从底部升起 60% 高抽屉）| 点面板内标签、`Esc`、点 `ⓘ` | `Esc` 或点 `ⓘ` → `lb-panel-closed` |
| `lb-panel-closed` | 面板收起，主图区**横向扩展到全宽**（不是留一条空白）| 点 `ⓘ`（或按 `I`）| → `lb-panel-open` |

### 4.3 灯箱键盘快捷键

| 键 | 行为 |
|---|---|
| `←` / `→` | 上一张 / 下一张（到边界时不循环，按钮置灰）|
| `Home` / `End` | 跳到第 1 张 / 最后一张 |
| `Esc` | **优先关元数据面板**；面板已关 → 退immersive；无 immersive → 关灯箱 |
| `I` | 切换元数据面板展开/收起 |
| `F` | 收藏/取消收藏当前图 |
| `Space` | 切换沉浸模式（immersive）|
| `+` / `-` | 缩放 100% ↔ 200%（在原图上）|
| `0` | 缩放复位为适应窗口 |

> ⚠️ **`Esc` 的优先级链是硬性要求**：`Esc` 必须是**逐级退出**（面板 → immersive → 灯箱），绝不能第一次按就关掉整个灯箱。用户的心理模型是"Esc 收掉当前最表层的东西"。

### 4.4 三个必须满足的恢复路径（明确列为验收项）

| 要求 | 实现方式 | 验收方法 |
|---|---|---|
| **① 关掉元数据面板后必须能再打开** | `ⓘ` 按钮**常驻**在底部工具栏右侧，不随面板收起而消失；且 `I` 键随时可唤出。面板状态存在组件 state，灯箱关闭后不清零（下次打开同一套图恢复上次状态）| 打开灯箱 → 点 `ⓘ` 关面板 → 确认 `ⓘ` 按钮仍在 → 点 `ⓘ` → 面板展开且内容完整 |
| **② 误触图片不能立刻把灯箱关掉** | **主图区域的单击不关闭灯箱**。单击行为是「切换沉浸模式」（隐藏 UI），这是可逆的。关闭灯箱只有 3 个显式入口：`Esc`（且需面板/沉浸都已退出）、右上角 `×` 按钮（≥ 44×44 px）、向下滑动手势（移动端，且需位移 > 80 px + 速度 > 0.5 px/ms 才触发，中途可撤销）| 打开灯箱 → 单击主图 → 灯箱**仍在**（只是 UI 隐藏）→ 再次单击 → UI 恢复 |
| **③ 加载失败不能死锁** | `lb-error` 状态提供 `重试`/`跳过` 两个显式按钮 + 自动降级（5 s 超时自动跳过到下一张，并在角落显示「已跳过 2 张」）| 断开图片文件 → 加载 → 出现错误态 → 点 `跳过` → 成功进入下一张 |

```
coser 前缀 (100) > 角色标签精确 (90) > 联合coser/别名 (85) > 作品标签精确 (80)
> coser 子串 (70) > 主题/未分类精确 (60/55) > 标签前缀 (60) > 原始目录名子串 (30)
```

**交互细节**：
- 输入 **debounce 120 ms**，结果显示 ≤ 80 ms（索引常驻内存，匹配是 O(n) 遍历 5292 条，实测 < 10 ms）
- 输入框下方给**分组建议**（见 §5.8）：`角色标签 (5)` / `coser 名 (2)` / `作品 (12)` / `套图 (8)`，**标明命中字段**，点击直接跳转
- `↑` `↓` 切换建议，`Enter` 选中第一个，`Esc` 清空建议但**不清空输入框内容**
- 支持多词：`纸悦 鸣潮` → 空格分隔，每词独立匹配（AND 关系）

### 5.2 标签筛选

**多标签逻辑**：
- **同一维度内**（如同时选 3 个作品）：**OR**（任一命中即显示）—— 因为作品是互斥的分类，选 3 个作品意为"这三个作品都要看"
- **不同维度间**（如作品=鸣潮 且 主题=泳装）：**AND**—— 这是最常见的精确检索需求

**AND/OR 切换**：
- 提供全局开关，位于筛选区顶部，标注为「同时满足（AND）」「任一满足（OR）」
- **默认 AND**（跨维度）。理由：跨维度 AND 覆盖 90% 的真实意图；同维度固定 OR，不受开关影响（避免"选 3 个作品要求同时是 3 个作品"的荒谬结果）
- 开关状态写入 URL（`?mode=and|or`），可分享
- 切换时**不重置已选标签**，只改变结果集

**标签点击行为**：
- 标签页点标签 → 跳 `/` 并应用筛选（§1.5）
- 卡片上的标签点 → **就地展开筛选**（不跳转），避免打断浏览
- 已选中的标签在卡片上有实心态 + `✓`

### 5.3 筛选状态持久化

| 状态 | 存储位置 | 理由 |
|---|---|---|
| 已选标签 / 搜索词 / AND-OR 模式 / 排序 | **URL query** | 可分享、可刷新、可后退。参数：`?q=xxx&w=鸣潮&r=爱弥斯&t=泳装&mode=and&sort=newest` |
| 视图密度（舒适/紧凑）| `localStorage` | 纯偏好，与具体内容无关 |
| 标签页上次维度 + 滚动位置 | `sessionStorage` | 跨页面跳转时恢复（§1.5）|
| 灯箱当前图索引 | **URL query**（`?i=12`）| 后退键可关闭灯箱（§1.4）|
| 收藏夹 | `localStorage`（本地）+ 可选文件导出 | 无后端时唯一可靠方案 |
| 人工标签修正 | `library-overrides.json`（文件）| 需跨会话持久且可版本管理（§5.4）|

**URL 长度保护**：标签数超过 8 个时，改用短 hash ID（`?f=h7a2k9`），映射表存 `sessionStorage`。避免 URL 超长导致浏览器拒绝或分享链接被截断。

### 5.4 标签类型就地修正（数据质量的可持续解法）

在元数据面板的每个标签旁提供下拉：`[作品 ▾] [角色 ▾] [主题 ▾] [未分类 ▾]`。

- 修正立即写入 `library-overrides.json`（格式：`{"爱弥斯": "role", "Fate": "work"}`）
- 下次启动时，Pass 1 构建词表时把 overrides 合并进去 → **人工修一次，永久生效**
- 提供「导出 / 重置修正」入口
- 修正后重新计算该标签影响的所有套图的分类（增量重算，实测全量只需 267 ms，可接受）

**这是本规范对"元数据只有目录名"这一根本约束的正面回答**：算法负责 80%，人工负责 20%，且人工成果被持久化并回流到算法。

### 5.5 空结果

**绝不显示"没有找到任何内容"就结束**。空结果页必须包含：

```
┌────────────────────────────────────────┐
│  没有匹配「爱弥斯 + 泳装」的套图         │
│  ─────────────────────────────────────  │
│  当前筛选：                            │
│  [角色: 爱弥斯 ×] [主题: 泳装 ×]        │
│  ─────────────────────────────────────  │
│  试试：                                │
│  · 移除「泳装」 → 3 个结果             │  ← 带预览数量的建议
│  · 放宽到「任一满足」→ 12 个结果      │
│  · 在全部套图中搜「爱弥斯」→ 5 个结果  │
│  ─────────────────────────────────────  │
│  [清空全部筛选]                        │
└────────────────────────────────────────┘
```

**硬性要求**：
- 空结果时**保留筛选 chips 可见**（否则用户不知道自己在筛什么）
- 每个放宽建议**带预估结果数**（实时算，< 10 ms）
- 提供一键清空
- 搜索无结果时，额外展示「相近的 coser」（编辑距离 ≤ 2 的 top 5）→「你是不是要找 `纸悦Etsu_ko`？」

### 5.6 标签筛选区的分层结构（回应「3613 个标签极度长尾」）

**问题**：唯一标签 3613 个，其中 85.4% 只出现 1–4 次。平铺必然是一堵墙。

**方案：两层结构 + 一个搜索框，不做「显示更多」**

```
┌─ 侧栏 · 标签筛选 ──────────────────┐
│ [🔍 筛选标签…            ]  ← 覆盖全部 3613 个
│ ───────────────────────────────── │
│ 热门 · 全部出现 ≥20 次（34 个）     │  ← 默认展开，显式列出
│ [兔女郎 87][女仆 49][旗袍 49]      │
│ [JK 41][泳装 38][柴郡 31]         │
│ [大凤 30][Fate 28][自拍 27]        │
│ …（共 34 个，3 行内排完）          │
│ ───────────────────────────────── │
│ 次热门 · 5–19 次（182 个）          │  ← 默认展开
│ [展开 ▾] 展开后按字频分组          │
│ ───────────────────────────────── │
│ 未分类 · 仅 others（2360 套图）      │  ← 默认展开，不折叠
│ [未分类标签 2360]                  │
└────────────────────────────────────┘
```

**具体规则**：

| 规则 | 数值 |
|---|---|
| 热门层阈值 | 出现 **≥ 20 次** → **34 个**标签，全部显式列出，不折叠 |
| 次热门层 | 出现 **5–19 次** → 182 个，**默认展开**，展开后按字首分组（拼音/Unicode 序） |
| 中间层（2–4 次，3087 个）| **不做平铺**，只能通过搜索框到达。理由：这批标签本身无浏览价值（每 2–4 个套图才出现一次），平铺出来是纯噪声 |
| 超长尾（1 次，310 个）| 同上，只能搜索到达 |
| 未分类桶 | **默认展开**（覆盖 2360 套图 = 44.6%，折叠等于让近半数据不可达）|
| 搜索框 | 覆盖**全部 3613 个**，支持 `key()` 归一化（`NIKKE`/`nikke` 折叠）；输入 ≥ 1 字符即出结果 |
| 排序 | 热门层按频次倒序；次热门层按频次倒序；搜索结果按**频次 × 匹配质量**（coser 前缀 100 > 标签精确 90 > 标签前缀 60 > 目录名子串 30）|
| 单行容量 | 侧栏宽 240 px，一行 2–3 个胶囊；热门层 34 个占 12 行以内 |
| 胶囊显示 | 只显示标签名 + 右侧数字（数字用次级色），**不显示分类图标**（除非置信度 ≥ 0.65）|

**关键决策**：**中间层不做「显示更多」**。常见做法是"显示更多 → 一次展开 500 个"，但那仍是一堵墙（3087 个）。既然 85.4% 的标签只出现 1–4 次，用户主动搜索的概率远高于浏览 —— 搜索框才是正确的主入口。

### 5.7 无标签套图的卡片呈现（回应「30% 套图无任何标签」）

**问题**：口径 A（`works/roles/themes/others` 全空）= **1435 套图（27.1%）**，卡片没有任何副标题可用。

**方案：卡片信息区的三级降级**

```
卡片结构（固定高度，不因内容缺失而跳动）：
┌─────────────┐
│             │  ← 封面（3:4，thumb 字段直指已生成的 240×308 JPEG）
│   封面       │
│             │
├─────────────┤
│ 标题行      │  ← coser 名（永远存在，解析率 99.98%）
│ 副标题行    │  ← 标签（按下方降级规则）
└─────────────┘
```

**副标题的四级降级**（从上到下取第一个可用者）：

| 优先级 | 条件 | 副标题显示 |
|---|---|---|
| 1 | 有作品/角色/主题标签 | `作品 · 角色 · 主题`（最多 3 个，超出用 `+N`）|
| 2 | 仅有 others 标签 | 前 2 个 others 标签 + `未分类` 标记（虚线边框胶囊）|
| 3 | **完全无标签（1435 套图，27.1%）** | **显示 `原始目录名`**（等宽字体、12px、次级色、单行省略号）|
| 4 | 原始目录名也过长（> 24 字符）| 取目录名**首段**（第一个 ` - ` 之前，即 coser 段）+ `…` |

**关键决策**：**第 3 级用原始目录名兜底，而不是留空**。理由：
- 留空会让 30% 的卡片看起来像"加载失败"或"内容缺失"，用户会怀疑坏了；
- 原始目录名**至少包含 coser 名**（解析率 99.98%），所以不是乱码；
- 与 §4.5「元数据面板必须展示原始目录名」一致 —— 同一信息在两处出现，用户能建立心智模型。

**缩略图墙（多图叠影）—— 结论：不做**
- 需求是「用缩略图墙代替文字」，我实测评估后**否决**：
  - 卡片宽度仅 240 px（3:4 封面），叠 3 张会每张只剩 ~72 px，人物已不可辨认；
  - 缩略图墙需要 3 次图片请求/卡（5292 卡 = 15876 请求），与 §8 的性能预算冲突；
  - 已经有 `thumb` 字段的单张封面 + `n` 字段（张数），信息量足够：`「12 张」`比三张糊图更有用；
- **替代方案**：在封面右上角叠加**张数徽标**（`n` 字段，实测已有），信息密度更高且零额外请求。

**长 coser 名截断**（回应议题 5）：
- 标题行**单行**，`text-overflow: ellipsis`，最大宽度 = 卡片内容区（240 - 2×12 = 216 px）
- 截断后仍可读性优先：字号 13px / 字重 600，约可容纳 **11–12 个汉字**或 **18–20 个拉丁字符**
- **完整名在两处可得**：卡片 `title` 属性（原生 tooltip）+ 灯箱/套图页的大标题处完整展示
- **双 coser 合集**（`#水淼 & #清水由乃`、`#西园寺南歌& #葵酱Aoi`）：
  - 标题显示 `水淼 & 清水由乃`（`&` 归一为 ` & `，两侧加空格）
  - **不做"主 coser + N 人"缩写** —— 缩写会让用户无法确认要找的人是否在列表里
  - `co` 字段在套图页元数据面板中单独列出：`合集 coser：2 位`

### 5.8 跨字段搜索（回应「标签是唯一导航入口」）

**问题**：用户想「看某个角色的所有写真」，但角色名可能出现在 3 个字段：coser 名、作品名、角色标签。

**结论：搜索必须跨字段，且必须区分「命中字段」以避免误导**

**搜索范围与权重**（`index.final.json` 的实际字段）：

| 字段 | 权重 | 匹配方式 | 示例 |
|---|---|---|---|
| `coser` | **100**（前缀）/ 70（子串）| 前缀优先 | `纸悦` → 纸悦Etsu_ko |
| `roles`（角色标签）| **90**（精确）/ 60（前缀）| 精确优先 | `爱弥斯` |
| `works`（作品标签）| **80**（精确）| 精确 | `鸣潮` |
| `themes`（主题标签）| **60**（精确）| 精确 | `兔女郎` |
| `others`（未分类标签）| **55**（精确）| 精确 | `Fate` |
| `raw`（原始目录名全文）| **30**（子串）| 子串 | `25年12月计划A` |
| `co` / `alias`（联合 coser / 别名）| **85** | 精确 | `清水由乃` → 含该 co-coser 的套图 |

**关键设计：结果分组显示，标明命中字段**

搜索框下拉结果**必须分组**并显示命中来源，否则用户会困惑"为什么搜 `碧蓝航线` 出来一堆 coser 名"：

```
🔍 爱弥斯
├─ 角色标签 · 5 个套图
│   #纸悦Etsu_ko - #鸣潮 #爱弥斯
│   #YoKei 约柯 - #鸣潮 #爱弥斯
│   …
├─ coser 名 · 2 个套图
│   …
└─ 全部结果（12）→  [查看全部]
```

**分组规则**：
- 每组最多显示 **4 条**，底部给「查看全部 N 个」链接
- 组间按权重降序：角色标签 → coser 名 → 作品 → 主题 → 未分类 → 目录名
- 组标题即命中字段名（`角色标签` / `coser 名` / `作品` / `主题` / `未分类` / `目录名`）

**归一化**：所有字段统一走 `key()`（NFKC + 小写 + 去符号空格），因此 `NIKKE`/`nikke`、`兔女郎`/`兔 女郎` 命中同一结果。**罗马音**（`Aimes` → `爱弥斯`）需额外映射表，**当前不实现**（无可靠音译库，猜错比不搜更糟），但**预留接口**：`lexicon.romanization` 为空时该能力关闭。

**「标签是唯一导航入口」的应对**：
- 标签页（L1-B）按维度分组时，**每个标签项旁显示"套图数 + 3 张缩略图条"**，让用户不点进去也能判断
- 搜索结果里的标签分组，**点击标签名 = 应用筛选**（跳 L1-A），**点击套图条目 = 直接进 L2**

### 5.9 emoji 标签与日文标签的呈现（回应议题 4）

**emoji 标签处理规则**（三档）：

| 情形 | 实例 | 处理 |
|---|---|---|
| emoji + 文字 | `#圣诞🎄` | **保留文字** `圣诞` 作为可搜标签；emoji 作为**装饰**显示在胶囊右侧（16px）|
| 纯 emoji | `#💜` `#🐭🧀` | **丢弃**该标签（不显示、不可搜）；emoji 整体作为装饰标记附在卡片上 |
| emoji 在 coser 名中 | `#ChuChu♡MAGIC` | `♡` 属装饰符号（U+2661），**保留在 coser 名中**（它是名字的一部分）|

> ⚠️ **关键区分**：emoji 作为**标签内容**时剥离（无语义、不可搜）；emoji 作为**名字的一部分**时保留。实测 `#真宝 - #圣诞🎄` → 标签 `圣诞`，emoji `🎄` 存 `emoji` 字段作装饰。
> **产品决策：emoji 永远不作为可筛选标签**（§3.7）。

**emoji 的胶囊渲染**：
- 不转成图标、不单独占位，**跟在文字标签后面**，用 `font-size: 13px`（比文字小 3px）以示从属
- 胶囊整体仍是可点击的筛选按钮（点击 = 按文字部分筛选）
- `aria-label` 读作「圣诞，装饰符号 圣诞树」

**日文标签的呈现**：
- 字体：与中文标签**同族**（不引入第三套字体），字重 **500**（比中文标签的 400 稍重），因为日文假名笔画密度低、需要稍加重才能在小字号下保持可辨识
- 行高：`line-height: 1.55`（比中文的 1.5 略高），避免假名上下标（`ゃゅょ`、浊音符号）被裁切
- 字号：与中文标签一致（13px）
- 断行：`word-break: keep-all` + `overflow-wrap: anywhere` —— 日文无词间空格，必须允许任意位置断行；`keep-all` 防止行首出现浊音符号
- 混排标签（如 `Frieren Blue Valley Dress` 拉丁 + 中文混排）：拉丁部分用 `font-variant-numeric: tabular-nums` 不必要，**不做特殊处理**，统一 `lang` 属性由浏览器自动选字体

**CJK 与拉丁的标签胶囊宽度差异**：实测拉丁标签（如 `Swimsuit The Herta`）明显长于中文标签，胶囊**不做等宽**，但**最大宽度 200 px** + 超出省略（`text-overflow: ellipsis`），保证侧栏不被撑破。

三档，**断点值取自设备实测主流宽度**，非 Tailwind 惯例。

> ⚠️ **与视觉规范的分工**：本表的**侧栏行为与工具栏形态**由本规范定义；**网格列数与容器几何**由 `01-visual-direction.md` §5.1 定义（列数是几何问题，视觉方已基于 1680px 容器完成实测算式）。两套断点**独立生效**，不要求在同一点切换。

| 档 | 范围 | 侧栏 | 工具栏 | 网格列数 | 灯箱 |
|---|---|---|---|---|---|
| **手机** | `< 768 px` | **底部抽屉**（从下滑出，高 80% 屏宽全屏，含遮罩；点遮罩关闭）| 顶栏压缩为：搜索框（占满）+ 筛选按钮（带角标数字）+ 排序下拉 | 见视觉规范 §5.1（620–859→3 · 400–619→2 · <400→1）| 全屏；元数据面板为**底部抽屉**（60% 高，可拖拽展开到 90%）；缩略图条隐藏，改用「上一张/下一张」大按钮 + 滑动 |
| **平板** | `768 px – 1279 px` | **图标栏**（宽 64 px，只显示图标 + tooltip；点「标签」图标展开为 280 px 浮层）| 完整单行：搜索 + 视图 + 排序 | 见视觉规范 §5.1（860–1099→4 · 1100–1279→5）| 图片居中不缩满，元数据面板为右侧 320 px 覆盖层（半透明遮罩 40%）|
| **桌面** | `≥ 1280 px` | **常驻**（宽 240 px，可手动折叠到 56 px 图标栏；折叠状态持久化到 localStorage）| 完整单行 + 右侧「视图密度」分段控件 | 见视觉规范 §5.1（1280–1439→5 · ≥1440→6）| 图片区 + 右侧常驻元数据面板 320 px（并排，不覆盖）；缩略图条常驻底部 |

### 6.1 具体规则

- **列宽**：卡片采用**固定宽高比 3:4**（`aspect-ratio: 3 / 4`）。容器宽 = `(可用宽 - 间距×(列数-1)) / 列数`。封面用 `object-fit: cover`。
  > **与视觉规范的对齐点**：实测图片比例分布为 **竖版 76.9% / 横版 22.8% / 方版 0.3%**（2859 张抽样），中位宽高比 **0.666（2:3）**，主比例 0.67 与 0.75（3:4）合计占 62%。因此：
  > - **目录墙封面**用 3:4 裁切（`cover`）是安全的 —— 主体居中裁切不会切掉人物；
  > - **单套图详情页**必须按**图片原生比例** `height:auto` 展示，**不得裁切**，否则会切掉 22.8% 的横构图人物；
  > - 这与 `01-visual-direction.md` §5.1 的规定一致，本规范予以确认。
- **列数断点**：以视觉规范 §5.1 的 6 档为准（`≥1440: 6 · 1100–1439: 5 · 860–1099: 4 · 620–859: 3 · 400–619: 2 · <400: 1`），本规范的三档（手机 / 平板 / 桌面）仅用于**侧栏行为与工具栏形态**的切换判定：
  | 行为维度 | 手机 | 平板 | 桌面 |
  |---|---|---|---|
  | 判定范围 | `< 768 px` | `768–1279 px` | `≥ 1280 px` |
  | 侧栏 | 底部抽屉 | 64px 图标栏 | 240px 常驻（可折叠 56px）|
  | 工具栏 | 搜索 + 筛选按钮 + 排序下拉 | 完整单行 | 完整单行 + 视图密度分段控件 |
  | 缩略图条 | 隐藏（用大按钮 + 滑动）| 常驻 | 常驻 |
  > **注意**：列数（6/5/4/3/2/1）与侧栏行为档位是两套独立维度，**不要求在同一点切换**。例如 860–1099 px 属于"平板"档（图标栏），但网格是 4 列。
- **缩略图条**：仅 ≥ 768 px 显示。宽 96 px 高 64 px，横向滚动，当前项带 2 px 选中边框。
- **触摸目标**：所有可点击元素 ≥ **44 × 44 px**（移动端）、≥ **32 × 32 px**（桌面）。相邻目标间距 ≥ 8 px。
- **断点切换时的状态保持**：从手机抽屉切到桌面常驻时，抽屉内的滚动位置和已展开分组要迁移到常驻侧栏。
- **横屏手机**（< 768 px 但高度 < 500 px）：灯箱隐藏缩略图条，元数据面板改为半屏；网格降为 3 列。
- **平板分屏**：宽度按视口而非设备判定，用 `matchMedia` 而非 `userAgent`。
- **缩放 200%**（浏览器缩放）时布局不得横向滚动（WCAG 1.4.10 Reflow）→ 用 `em`/`%` 而非固定 px 容器宽。

## 7. 无障碍与可读性

### 7.1 对比度（WCAG 2.1 AA）

| 对象 | 要求 | 备注 |
|---|---|---|
| 图片上叠加的**标题文字** | **≥ 4.5:1**（正文大小）| 关键难点，见 §7.2 |
| 图片上叠加的**元数据小字**（如 "12 张 · 39 MB"）| **≥ 4.5:1** | 同上 |
| 大号文字（≥ 24 px 或 ≥ 18.66 px 粗体）| **≥ 3:1** | 卡片上的 coser 名若 ≥ 24 px 可放宽 |
| 正文 / 标签文字对背景 | **≥ 4.5:1** | — |
| 界面组件边界、图标、焦点环 | **≥ 3:1**（WCAG 1.4.11）| 未选中的 chip 边框也需达标 |
| 禁用态文字 | 无硬性要求，但**不得低于 3:1** | 避免"看不清为什么不能点" |

### 7.2 图片上叠文字的对比度余量（给视觉方的硬约束）

图片内容不可控（明暗不定），**必须用遮罩保证对比度**。规范给出可执行方案：

1. **卡片底部渐变遮罩**：从 `rgba(0,0,0,0)` 线性过渡到 `rgba(0,0,0,0.85)`，过渡高度 = 文字区高度 × 1.6，最小 56 px，方向自下而上。
2. **遮罩最低不透明度 0.60**，且渐变终点必须 ≥ 0.85。
3. **实测校验要求**：文字与**遮罩终点色**（不是图片本身）的对比度 ≥ 4.5:1。若文字是白色（#FFFFFF），遮罩终点需 ≥ 0.60 的黑；若文字是浅色，遮罩终点需 ≥ 0.75。
4. **浅色图片的极端情况**：若封面图平均亮度 > 0.75，遮罩不透明度提升一档（0.60 → 0.78）。此判定在缩略图生成时计算并存入索引（`coverLuma` 字段），运行时零成本。
5. **禁止**：不使用无遮罩的文字直接叠图；不使用半透明毛玻璃（`backdrop-filter`）作为唯一保障手段（Safari < 15 不支持 → 降级后对比度失控）。毛玻璃只能作为**附加**层，其下方必须有实色遮罩兜底。
6. **纯文字标题场景**（如套图列表页）不涉及图片对比度，正常走 §7.1 表格。

> ⚠️ **给视觉方向的约束（需求，不指定实现）**：卡片叠字区域必须有可预测的最暗遮罩带；不使用纯色半透明覆盖整卡（会压掉图片主体）。

### 7.3 焦点态与键盘可达

- **焦点环**：2 px 实心描边 + 2 px 偏移，颜色对相邻区域对比 **≥ 3:1**。深色背景用亮色环，浅色背景用深色环（`prefers-color-scheme` 双套）。
- **`:focus-visible`**：仅键盘导航时显示焦点环，鼠标点击不显示（但**不隐藏 outline** 于 `:focus`）。
- **焦点顺序**：DOM 顺序 = 视觉顺序（从上到下、从左到右）。网格用**方向键**在卡片间移动（↑↓←→），`Enter` 打开套图，`Space` 选中（多选），`Esc` 清空选择。
- **模态陷阱**：灯箱打开时，焦点锁在灯箱内；`Esc` 逐级退出；**关闭后焦点回到触发元素**（打开灯箱的那张卡片）。
- **跳至主内容**：提供视觉隐藏但可聚焦的「跳到主要内容」链接，位于页面首个焦点位。
- **筛选侧栏**：所有 chip 是真实 `<button>`，带 `aria-pressed`；侧栏可折叠时用 `<button aria-expanded>` 控制。

### 7.4 图片 alt 文本生成

**规则**：

```
alt = "{coser} · {作品} {角色} {主题} · 第 {i}/{n} 张"
```

- 无 coser → `"{作品} {角色} · 第 {i}/{n} 张"`
- 全部解析不出 → `"{原始目录名} · 第 {i}/{n} 张"`
- **长度上限 125 字符**，超出则截断到 122 + `…`
- **不要**把 alt 写成"图片"、"写真 1.jpg"这类无信息文本
- 装饰性元素（分隔线、图标）用 `alt=""` + `aria-hidden="true"`

实例：
```
alt="纸悦Etsu_ko · 鸣潮 爱弥斯 · 第 3/12 张"
alt="九柒喵 · 碧蓝航线 柴郡 兔女郎 · 第 7/19 张"
alt="星黛鹿鹿 · 私房 黑丝 女仆 · 第 2/39 张"
```

**网格模式下的节流**：5292 张卡片全量带 alt 会让读屏器一次性朗读数百条 → 网格用 `role="grid"`，卡片 `aria-label` 包含套图摘要（不含逐张 alt）；逐张 alt 只在灯箱中提供。

### 7.5 触控与指针

- 所有可点击元素 ≥ 44 × 44 px（移动端）
- 相邻可点击目标间距 ≥ 8 px
- 灯箱「上一张/下一张」按钮：移动端 ≥ 48 × 48 px，位于屏幕左右边缘，纵向居中
- **悬停专属信息**（如缩略图预览）必须有**点击/触摸等价入口**（见 §7.6 immersive 模式）

### 7.6 `prefers-reduced-motion`

| 动效 | 正常 | reduced-motion |
|---|---|---|
| 灯箱主图交叉淡入 | 120 ms | **0 ms**（直接替换）|
| 卡片 hover 放大 | scale 1.03 / 150 ms | **禁用**（仅改变边框/阴影）|
| 网格滚动入场动画 | 逐个淡入 | **禁用** |
| 收藏心形弹跳 | scale 1→1.25→1 / 200 ms | **仅颜色变化**，无缩放 |
| 抽屉滑出 | 250 ms | 保留位移但**时长降至 0 ms**（直接显示）|
| 骨架屏 shimmer | 1.2 s 循环 | **改为静态灰块**（无动画）|

实现：全局 `@media (prefers-reduced-motion: reduce) { *, *::before, *::after { animation-duration: 0.01ms !important; transition-duration: 0.01ms !important; } }`，但**保留 opacity 变化**（避免闪烁）。

### 7.7 其他 ARIA 要求

- 网格：`role="grid"`，行 `role="row"`，卡片 `role="gridcell"` + `tabindex="-1"`（roving tabindex）
- 灯箱：`role="dialog" aria-modal="true" aria-label="图片查看器"`
- 筛选结果数：`aria-live="polite"`，筛选变化时播报「共 24 个套图」
- 加载态：骨架屏容器 `aria-busy="true"`，加载完成移除
- 进度（灯箱载入中）：`role="progressbar"` + `aria-valuenow` + `aria-valuetext="载入中 3/12"`
- 快捷键面板：`<dialog>` + `aria-modal`，`Esc` 关闭，焦点锁在面板内

### 8.2 首屏策略：索引已预生成，前端零扫描

**决策变更**：原计划「首屏只索引目录层 + 后台补齐张数」→ **已由 `index.final.json` 落地**，前端不需要任何文件系统访问。

**前端启动序列**：

| 步 | 动作 | 预算 |
|---|---|---|
| 1 | `fetch('index.final.json')` | 4,900 KB，本地 ≈ 80–150 ms |
| 2 | `JSON.parse` + 建立倒排索引（标签 → set id 列表）| 120–180 ms |
| 3 | 渲染首屏 24 张卡片（封面走 HTTP 缓存，`thumb` 字段直指 240×308 JPEG）| ≈ 200 ms |
| 4 | **首屏可交互** | **≤ 1200 ms** ✅ |

**已落地的字段**（`index.final.json` 每条 set）：
`id raw coser tags works roles themes others co series pages size times emoji promo n path thumb files`

**`n` 字段（真实张数）已由预生成索引提供**，因此 §5.7 卡片副标题的第 4 级「张数徽标」**无需运行时补齐**，直接渲染 `n` 即可。

> ⚠️ **仍然有效的约束**：前端**不得**在运行时遍历文件系统补数据。所有字段以 `index.final.json` 为唯一事实源。

### 8.3 虚拟滚动：必须做

**结论：网格必须虚拟滚动。**

- 5292 张卡片，总高度 = 5292 / 6 列 × 卡片高(≈ 320 px) ≈ **282,000 px**（桌面 6 列；平板 4 列时约 423,000 px）
- 虚拟滚动后 DOM 节点数 = **可见行数 + 缓冲 2 行** ≈ **18 个**
- 方案：固定行高 + 绝对定位（不用动态测量，避免测量抖动）。卡片高 = 封面高(宽×4/3) + 信息区 76 px，**行高固定**即可。
- **筛选后重算**：筛选改变时重算总高并 `scrollTo(0)`；**保留筛选前的滚动位置**通过 URL 存 `?page=` 或 `scrollY`（见 §5.3）

**单套图内部**：最大 877 张 → 同样虚拟滚动（网格视图）。照片流模式（单列）用**分页预取**而非虚拟滚动（连续阅读体验更好）。

### 8.4 缩略图：已预生成，运行时零成本（Phase 3 已落地）

**状态变更**：原「绝不批量预生成 + 运行时三层缓存」方案**已不需要**。实际落地情况：

| 项 | 实测值 |
|---|---|
| 封面缩略图数量 | **5292 张**（每个套图 1 张，1:1 对应）|
| 尺寸 / 格式 | **240 × 308 px JPEG**（比例 ≈ 0.779，与卡片 3:4 略有差异，`object-fit: cover` 裁切）|
| 总体积 | **67 MB** |
| 路径 | `app/assets/thumbs/` |
| 索引字段 | `thumb`，直指相对路径（如 `thumbs/ta86281.jpg`）|

**前端规则**：
- 卡片封面 **直接 `<img src="{thumb}">`**，不加载占位图后再替换（无闪烁）
- **必须**加 `loading="lazy"` + `decoding="async"`
- **必须**设 `width="240" height="308"`（或 CSS `aspect-ratio`）以避免 CLS
- 缩略图走 HTTP 缓存，**浏览器自动管理**，前端不需要实现 LRU/磁盘缓存
- 67 MB 全量缩略图**不阻塞首屏** —— 虚拟滚动只加载视口内 24 张（≈ 300 KB）

**兜底预案**（仅当某套图的 `thumb` 字段缺失或 404）：
- 降级到该套图 `files` 数组的第 1 张原图 + CSS `object-fit: cover`
- 若原图也失败 → 显示中性占位块 + 套图名首字（**不留破图**）

**仍然适用的约束**：
- ⚠️ **不得**为套图内的 72732 张原图生成缩略图（按 60 ms/张 = 73 分钟）。当前只生成了 5292 张**封面**，套图内部详情页直接用原图（单张 90–800 KB，本地读盘 20–60 ms）。
- 套图详情页的缩略图（详情页网格）**直接用原图** + `loading="lazy"`，实测套图 p50=10 张、p99=61 张，规模可接受。

### 8.6 分页 vs 无限滚动

**决策：都不用于主网格，用虚拟滚动。** 分页在图片浏览场景是反模式（用户想扫视，不是在找第几页）。但：

- **「最近新增」页用「加载更早」按钮**（每次 30 天），因为时间线天然有边界感
- **单套图内（照片流模式）用连续滚动 + 预取**，不是分页
- **超长套图（> 300 张）** 额外显示「跳到第 N 张」输入框（877 张时纯滚动过长）

### 8.7 排序实现的性能注意

- 排序字段：`最近新增`（套图拍摄日期众数）、`图片数`、`coser 名`
- **排序结果在索引构建时预计算一次**，运行时排序 5292 条 = < 5 ms
- 「最近新增」排序**依赖 Pass 2 提取的文件名日期**，这需要读文件名 → **归入 §8.2 的 P1 后台批次**，前 200 个先出结果，滚动时渐进补齐

## 9. 反模式清单

> 每条都附**在本库真实数据上会发生的具体后果**。

### ❌ 反模式 1：一次性把 5292 个套图塞进 DOM

**后果**：5292 卡片 × 平均 3 标签 = 20000+ DOM 节点。首屏渲染 > 3 s，滚动帧率 < 20 FPS，内存 > 800 MB，低端机直接崩溃。
**正确做法**：虚拟滚动，DOM 节点恒定 ≤ 18 个（§8.3）。

### ❌ 反模式 2：把原始目录名直接当标题显示

**后果**：用户看到 `#纸悦Etsu_ko - #鸣潮 #爱弥斯` 这种字符串——含 `#` 号、含 `-` 分隔符、含 `[39P-390MB]` 噪声。实测 1313 个目录（24.8%）根本没有 `-` 分隔符，直接显示会让界面看起来像日志而非产品。
**正确做法**：显示解析后的 `coser · 作品 · 角色`；**原始目录名放在元数据面板内**（可复制，等宽字体），不作为主标题。

### ❌ 反模式 3：把 85404 个文件一次性索引进内存

**后果**：全量索引需 801 ms 扫描 + 巨大内存占用，且 95% 的文件在首屏不可见。
**正确做法**：首屏只索引目录层（§8.2），文件层按需读取。

### ❌ 反模式 4：为套图内的 72732 张原图生成缩略图

**后果**：72732 张 × 60 ms = **73 分钟**的启动阻塞，或一次性吃掉 3–5 GB 磁盘。
**正确做法**：**只生成封面**（5292 张，67 MB，已完成）；套图详情页直接用原图 + `loading="lazy"`（§8.4）。
> ⚠️ **注意不要误读**：本项目**确实预生成了封面缩略图**（5292 张，每个套图 1 张）—— 这是正确的，因为封面是列表页的必需项。**错误的是给套图内的每一张图都生成缩略图。**

### ❌ 反模式 5：把「作品 / 角色 / 主题」混在一个扁平的标签云里

**后果**：用户想找「爱弥斯」时，在 3613 个平铺标签里翻找；而 `#鸣潮`（作品）和 `#爱弥斯`（角色）视觉上无差别，用户不知道自己筛的是什么。**分类质量提升后 Top 20 里作品词已占前排**（碧蓝航线/蔚蓝档案/NIKKE/原神/鸣潮…），但主题词（兔女郎/女仆/旗袍/JK/泳装）仍占 5 席 —— 若不分组，用户按"作品"直觉点进去的仍可能是服装。
**正确做法**：三维分组（作品/角色/主题/未分类）+ **热门层/搜索框分层**（§5.6），且**未分类桶默认展开**（否则 44.9% 的套图不可达）。

### ❌ 反模式 6：只靠共现统计给标签分类，不给人工修正入口

**后果**：实测 `兔女郎`（82 次）会被判成作品、`私房`（10 次）会被判成角色、7 个长尾角色（`2B`/`尼禄`/`灰姑娘`）永远无法归类。用户看到错误的"角色：兔女郎"会永久失去信任。
**正确做法**：三层证据打分 + 置信度分档 + 低置信度不显示类型图标 + **就地修正并持久化到 overrides 文件**（§3.8、§5.4）。

### ❌ 反模式 7：把 `#` 标签、emoji、方括号规格当作可搜索/可筛选的标签

**后果**：搜索框里输入 `#` 搜不到任何东西；`[39P-390MB]` 变成一个"标签"；emoji `💜` 无法被搜索。
**正确做法**：解析阶段剥离，标签池只留干净文本（§3.3、§3.7）。

### ❌ 反模式 8：用目录 mtime 实现「最近新增」

**后果**：实测 5292 个目录的 mtime 全部落在 2026-10-23 ~ 10-25 三天内（批量拷贝所致），「最近新增」页会把 5292 个套图全部显示为"今天"，功能完全失效。
**正确做法**：用套图内文件名 `YYYYMMDD` 前缀的众数作为拍摄日期（§3.9）。

### ❌ 反模式 9：灯箱里点击图片就关闭

**后果**：用户在翻阅时想看细节（点一下放大/退出沉浸），结果误关灯箱，丢失"我在第 12 张"的位置，需要重新翻。
**正确做法**：单击主图 = 切换沉浸模式（可逆）；关闭只走 `Esc`（逐级）/ `×` 按钮 / 下滑手势（§4.4）。

### ❌ 反模式 10：元数据面板收起后找不到 reopen 入口

**后果**：用户关掉面板看图，想再看元数据却找不到按钮，只能关掉重开 → 位置丢失。
**正确做法**：`ⓘ` 按钮**常驻工具栏**，`I` 键随时唤出，面板状态在灯箱生命周期内保持（§4.4 ①）。

### ❌ 反模式 11：把运营/广告目录（`📌 近期精选（点击预览 👀）`）混进搜索结果

**后果**：实测 9 个这类目录会命中任何包含"精选/资源"的搜索，且它们**不是套图**（是引流位），点进去是空。
**正确做法**：解析阶段标 `promo=True`，默认不展示、不进索引；如需展示，单独放在独立的「运营位」区域。

### ❌ 反模式 12：搜索结果只显示"无结果"

**后果**：用户不知道是筛太严还是搜错了词，放弃使用。
**正确做法**：空结果页保留 chips、给带**预估数量**的放宽建议、给编辑距离 ≤ 2 的近似 coser（§5.5）。

### ❌ 反模式 13：不过滤 `.part` 文件

**后果**：实测库中有 **11 个 `.part` 文件**（Telegram 未下载完成的残片）。不过滤会导致：缩略图生成时解码失败 → 卡片出现破图；图片计数虚高；灯箱切到该图时进入永久加载态。
**正确做法**：文件枚举阶段硬过滤 `['.jpg','.jpeg','.png','.webp']`，`.part` 及其他一切扩展名一律排除。
